| | |
|---|---|
| **날짜** | 2026-08-06 |
| **Base URL** | `http://localhost:8000` (개발) |
| **인증** | Google 로그인 성공 시 발급되는 `HttpOnly` 세션 쿠키 (별도 표기 없으면 로그인 필수) |

## 1. 인증

### `POST /auth/google`
Google id_token을 검증하고 자체 세션 JWT를 `HttpOnly` 쿠키로 발급한다. JWT 원문은
응답 본문에 포함하지 않는다.

- 인증: 불필요
- Request
```json
{ "id_token": "eyJhbGciOi..." }
```
- Response `200`
```json
{
  "id": "uuid",
  "email": "user@example.com",
  "name": "홍길동"
}
```
- Response `401` — id_token 검증 실패

### `GET /me`
현재 로그인 사용자 정보 조회.

- Response `200`: 위 사용자 객체와 동일
- Response `401` — 토큰 없음/만료

### `POST /auth/google/redirect`
iOS Safari 등 ITP가 적용된 환경에서 팝업 콜백 대신 전체 화면 리디렉트로 로그인을
완료하는 경로. CSRF 이중 토큰 검증 후 `POST /auth/google`과 동일하게 세션 쿠키를
발급한다.

- 인증: 불필요
- Response `200`: `POST /auth/google`과 동일한 사용자 객체

### `POST /auth/logout`
세션 쿠키를 만료시켜 로그아웃한다.

- Response `204`

## 2. API 키 (BYOK)

2026-08-17부터 클라이언트 패스프레이즈 암호화로 전환됐다(설계:
`docs/superpowers/specs/2026-08-17-byok-client-side-encryption-design.md`).
브라우저가 Web Crypto(PBKDF2→AES-GCM)로 API 키를 로컬 암호화하고, 서버는
암호문만 저장·반환한다 — 평문은 등록 전 검증(`/verify`)이나 실제 provider 호출이
필요한 요청(`/test`, `POST /schedules` 등)에 그 요청 한정으로만 실린다.

### `POST /me/llm-credential/verify`
저장 전에 평문 키가 실제로 유효한지 provider에 핑을 보내 확인한다. **저장은 하지
않는다** — 프런트는 이 호출이 성공해야만 아래 `POST /me/llm-credential`을 호출한다.

- Request
```json
{ "provider": "anthropic", "api_key": "sk-ant-..." }
```
`provider`는 `anthropic`(Claude) / `openai`(GPT) / `upstage`(Solar) / `google`(Gemini) 중 하나.
- Response `200`
```json
{ "reply": "안녕하세요!" }
```
- Response `400` — 키 검증 실패 (`{"detail": "API 키 테스트에 실패했어요: ..."}`)
- Response `422` — `provider` 형식에 안 맞는 키(접두사 정규식 불일치)

### `POST /me/llm-credential`
클라이언트가 이미 암호화한 값을 그대로 저장한다. 이미 등록된 키가 있으면 교체(제공자 포함)된다.

- Request
```json
{
  "provider": "anthropic",
  "ciphertext": "base64...",
  "salt": "base64...",
  "iv": "base64...",
  "kdf_iterations": 600000,
  "masked_key": "sk-ant-••••••••uvwx"
}
```
- Response `200`
```json
{
  "provider": "anthropic",
  "masked_key": "sk-ant-••••••••uvwx",
  "ciphertext": "base64...",
  "salt": "base64...",
  "iv": "base64...",
  "kdf_iterations": 600000
}
```

### `DELETE /me/llm-credential`
등록된 키 삭제.

- Response `204`
- Response `404` — 등록된 키 없음

### `GET /me/llm-credential`
등록된 암호문 번들을 그대로 반환한다 — 브라우저가 로컬에서 복호화하려면
`ciphertext`/`salt`/`iv`/`kdf_iterations`가 필요하기 때문(서버는 복호화 안 함).

- Response `200`
```json
{
  "provider": "anthropic",
  "masked_key": "sk-ant-••••••••uvwx",
  "ciphertext": "base64...",
  "salt": "base64...",
  "iv": "base64...",
  "kdf_iterations": 600000
}
```
- Response `404` — 등록된 키 없음

### `POST /me/llm-credential/test`
프런트가 로컬 복호화한 평문으로 등록된 키를 재확인한다(서버는 스스로 복호화 못 함).

- Request
```json
{ "api_key": "sk-ant-..." }
```
- Response `200`
```json
{ "reply": "안녕하세요!" }
```
- Response `400` — 키 검증 실패
- Response `404` — 등록된 키 없음

## 3. 일정 생성 · 조회

### `POST /schedules`
조건을 입력받아 Step1(조건 정규화) → Step2(후보 생성) → Step3(검증·병합)까지
실행하고, **경로(routes) 없는** 3개 후보를 반환한다. 경로는 사용자가 후보 하나를
고른 뒤 `POST /schedules/{session_id}/routes`로 별도 조회한다(2026-08-10 파이프라인
순서 재설계 — `docs/AI파이프라인_Step별_설계_2026-08-09.md` "전체 흐름" 참고,
ODsay 호출 비용을 실제로 열어볼 후보 1개로만 제한하기 위함).

성공 응답의 `place_pool`에는 일정을 만들 때 실제로 검색한 장소 이력이 들어 있다.
`candidate_count`는 Step2에 전달한 중복 제거·비선호 제외 후 후보 수이고,
`groups`는 `liked`(선호 태그 검색), `disliked`(비선호라서 일정에서 제외한 검색
결과), `categories`(카테고리별 검색)로 나뉜다. 각 장소는 `place_id`, `name`,
`category`, `address`, `map_url`을 가진다. 이 스냅샷은 세션과 함께 DB에도 저장되어 추후
피드백 검색 시 재사용한다.

- Request

`liked_text`/`disliked_text`는 태그 선택이 아니라 자유 텍스트 그대로 받는다(각 최대
50자). Step1 조건 정규화(LLM)가 여기서 구조화 태그(`NormalizedConditions.liked_tags`
등)를 뽑아낸다 — 기술설계 §4 Step1.

`headcount`는 1~30, `budget_per_person`은 1,000~1,000,000원 범위만 허용한다
(2026-08-20, 사용자 결정) — 벗어나면 422.

`region`은 세부지역까지 포함한 문자열 하나만 받는다(예: `"서울 강남"`) —
2026-08-11(2차)부터 여러 지역 조합 지원을 포기했다. 네이버 지역검색 API의
`display`(최대 5)/`start`(페이지네이션 사실상 고정) 제약상 지역을 여러 개로
쪼갤수록 지역당 결과가 희석되는 역효과가 있어서, 지역 하나에 카테고리·태그
검색을 최대한 팬아웃해 후보 풀을 채우는 쪽으로 방향을 바꿨다(`AI파이프라인_
Step별_설계` 참고). 세부지역 없이 시/도만 보내면(예: `"서울"`) 422 —
프런트에서 먼저 걸러주고, 백엔드 `NormalizedConditions.validate_region()`이
다시 검증한다(기술설계 §4 Step1 참고).

```json
{
  "purpose": "date",
  "headcount": 2,
  "time_range": ["2026-08-15T10:00:00", "2026-08-15T21:00:00"],
  "region": "서울 강남",
  "liked_text": "날씨가 너무 더워서 실내 위주로, 콩국수나 텐동을 점심으로 먹고 싶어",
  "disliked_text": "해산물은 못 먹어요",
  "budget_per_person": 50000,
  "api_key": "sk-ant-...",
  "resolved_liked_tags": null,
  "resolved_disliked_tags": null
}
```
`api_key`는 클라이언트가 로컬에서 복호화한 평문(§2 참고) — 서버는 이 요청이
파이프라인을 호출하는 동안만 쓰고 저장하지 않는다.

`resolved_liked_tags`/`resolved_disliked_tags`(2026-08-20 추가)는 선택 필드다.
프런트가 `POST /schedules/normalize-preview`로 미리 확인한 뒤 사용자가 직접
충돌·오분류를 확정한 태그 목록(`PreferenceTag[]`, 아래 미리보기 응답과 같은
형태)을 그대로 실어 보내면, 서버는 Step1 LLM을 다시 호출하지 않고 이 값을 그대로
쓴다 — `time_range` 검증과 같은 이유(요청 직접 조작 방지)로 서버도
`cap_verifiable_tags()` 규칙을 이 값에 다시 적용한다. 둘 다
`null`(또는 생략)이면 기존처럼 `liked_text`/`disliked_text`를 서버가 LLM으로
정규화한다.

두 `resolved_*` 목록에 같은 `tag`가 동시에 있으면 서버가 `422`로 거절한다. 모달을
우회한 직접 API 호출에서도 어느 조건을 우선할지 조용히 결정하지 않기 위해서다.

### `POST /schedules/normalize-preview`
좋아요·싫어요 자유 텍스트만 Step1(조건 정규화)로 미리 돌려, 실제 일정 생성(Step2~4까지
실행하는 무거운 `POST /schedules`) 전에 사용자가 분류 결과·직접 충돌·상한 초과 태그·의미
충돌을 확인할 수 있게 한다(2026-08-20, `docs/입력_엣지케이스_개선계획_2026-08-14.md` 항목
1·2·3·4). 의미 충돌 판단은 좋아요·싫어요 둘 다에 verifiable 태그가 있을 때만 도는 조건부
LOW 티어 보조 호출이라, 평소엔 Step1 1콜과 다르지 않다.

- Request
```json
{
  "liked_text": "회는 빼고 파스타랑 초밥이 좋아요",
  "disliked_text": "초밥은 별로예요",
  "api_key": "sk-ant-..."
}
```
- Response `200`
```json
{
  "liked_tags": [{"tag": "파스타", "verifiable": true, "is_meal": true, "preference_kind": "food_menu", "priority": 3}],
  "disliked_tags": [{"tag": "초밥", "verifiable": true, "is_meal": true, "preference_kind": "food_menu", "priority": 3}],
  "dropped_liked_tags": [],
  "dropped_disliked_tags": [],
  "conflicting_tags": ["초밥"],
  "semantic_conflicts": [
    {"liked_tag": "새우튀김", "disliked_tag": "해산물", "explanation": "새우튀김은 해산물에 포함될 수 있어요"}
  ]
}
```
`conflicting_tags`는 `liked_tags`/`disliked_tags` 둘 다에 같은 문구로 들어간
태그다(태그가 이 배열에 있어도 위 두 목록에는 원래 분류대로 계속 나타난다 —
프런트가 충돌 UI로 강조만 한다). `dropped_liked_tags`/`dropped_disliked_tags`는
verifiable 태그 상한(5개)을 넘어 이번 일정에 반영되지 않는 태그. `semantic_conflicts`
(2026-08-20 추가)는 문구는 다르지만 의미가 겹칠 수 있는 쌍(예: 초밥은 해산물의
하위 개념)이다. 프런트는 같은 색 테두리로 충돌 쌍을 표시하고, 각 쌍에서
기존 태그의 좋아요/싫어요 이동 또는 제외 버튼으로 충돌을 해소하기 전에는 생성 요청을
보내지 않는다. 태그를 움직일 때마다 충돌을 다시 판단하고, 충돌이 사라지면 일반 태그
표시로 돌아온다. 최종 태그 목록은 `resolved_*`로 전송된다. 의미 충돌은 LLM의
보조 판단이므로 서버는 재호출해 422로 강제하지 않고, 결정적으로 같은 문구인 직접
충돌만 서버에서 422로 막는다.
- Response `404` — 등록된 API 키가 없음
- Response `200`
```json
{

  "place_pool": {
    "candidate_count": 57,

      "liked": [{"label": "와플", "places": [{"name": "OO와플", "category": "카페", "address": "서울 강남구 ...", "map_url": "https://map.naver.com/..."}]}],

    {
      "candidate_id": "A",

      "activities": [
        {
          "order": 1,
          "name": "OO파스타",
          "category": "식당",

- Response `404` — 등록된 API 키가 없음 (`GET /me/llm-credential`과 같은 메시지·상황)
- Response `422` — 필수 조건 누락 (조건 정규화 단계 실패)
- Response `422` — `resolved_liked_tags`와 `resolved_disliked_tags`에 같은 태그가 있음

  "adjustable_conditions": ["time_range", "budget_per_person"]
}
```

### `POST /schedules/{session_id}/routes`
사용자가 3개 후보 중 하나를 고르면, 그 후보에 한해 Step4(`enrich_routes`)를 실행해
구간별 이동 옵션을 채운 최종 1안을 반환한다(2026-08-10 라우터 구현 완료). 대중교통
(ODsay)은 한 구간에 여러 경로 대안이 있으면 전부 담고, 자차(NCP Maps Directions 5)는
실시간 빠른길 1개만 담는다. `recommended_option_id`는 이 함수가 계산한 기본값(최단
소요시간)이고, `selected_option_id`는 사용자가 실제로 고른 값 — 초기값은 같지만
프런트에서 사용자가 다른 옵션을 고르면 그 시점부터 달라진다(선택 자체는 서버에
저장하지 않고 프런트 상태로만 들고 있다가, 확정 시점엔 어떤 옵션을 골랐는지와 무관하게
`candidate_id`만 넘긴다).

- Request
```json
{ "candidate_id": "A" }
```
- Response `200`
```json
{
  "candidate_id": "A",
  "title": "실내 위주 알뜰 코스",
  "why_recommended": "예산 내에서 보드게임과 파스타를 모두 포함",
  "activities": [ /* Step4가 실제 이동시간 기준으로 재조정한 start_time/end_time 포함 */ ],
  "routes": [
    {
      "from_order": 1,
      "to_order": 2,
      "recommended_option_id": "transit-0",
      "selected_option_id": "transit-0",
      "options": [
        { "option_id": "walk", "mode": "walk", "duration_minutes": 15, "fare_krw": 0, "transfer_count": 0, "description": "" },
        { "option_id": "transit-0", "mode": "transit", "duration_minutes": 8, "fare_krw": 1400, "transfer_count": 0, "description": "지하철 강남 → 교대" },
        { "option_id": "car", "mode": "car", "duration_minutes": 12, "fare_krw": 2500, "transfer_count": 0, "description": "자동차(실시간 빠른길)" }
      ]
    }
  ],
  "feasibility_warning": null
}
```
- Response `404` — 존재하지 않는 일정 또는 후보
- Response `403` — 타인 소유 세션

### `GET /schedules/{session_id}`
저장된 일정 세션 조회 (본인 소유만).

- Response `200`: `POST /schedules` 응답과 동일한 `candidates` 포함 — `POST
  .../routes`를 아직 안 불렀으면 `routes`는 빈 배열. `share_slug` 필드도 같이
  내려준다 — 확정 전(draft)에는 `null`, 확정 후에는 `POST .../confirm` 응답에서
  받았던 것과 같은 slug. 확정 응답을 새로고침 등으로 놓쳐도 이 엔드포인트로
  다시 조회해 slug를 복구할 수 있게 하기 위함(2026-08-10).
```json
{ "session_id": "uuid", "candidates": [ "..." ], "share_slug": "aB3xK9pL" }
```
- Response `403` — 타인 소유 세션
- Response `404` — 존재하지 않음

### `GET /confirmed-schedules` / `GET /draft-schedules`
본인 소유 세션 목록. 확정본은 `ScheduleSummary`(제목/지역/후보 제목/생성일시/
`share_slug`), 초안은 `DraftScheduleSummary`(이어서 만들기용 최소 정보)를 각각
배열로 반환한다. "나의 일정" 화면(`ConfirmedSchedulesView`)이 두 목록을 함께
보여준다.

- Response `200`: `ScheduleSummary[]` / `DraftScheduleSummary[]`

### `PATCH /schedules/{session_id}/title`
일정 이름을 바꾼다(확정·초안 공통).

- Request
```json
{ "title": "친구들이랑 홍대" }
```
- Response `200`: `ScheduleSummary`
- Response `403` — 타인 소유 세션
- Response `404` — 존재하지 않음

### `POST /schedules/bulk-delete`
여러 세션을 한 번에 삭제한다(최대 100개).

- Request
```json
{ "session_ids": ["uuid", "uuid"] }
```
- Response `200`
```json
{ "deleted_count": 2 }
```

### `DELETE /schedules/{session_id}`
세션 하나를 삭제한다.

- Response `204`
- Response `403` — 타인 소유 세션
- Response `404` — 존재하지 않음

## 4. 일정 수정 · 피드백

### 필수 장소 선택·재생성

후보 목록의 장소를 사용자가 직접 고르면, 일반 후보가 아닌 **반드시 포함할 제약**으로
저장한다. 재생성은 최초 검색 풀과 정규화된 조건만 재사용하며 새 검색이나 Step1 호출을
하지 않는다. Step2는 선택 장소 중심으로 클러스터를 다시 만들고, Step3는 모든
`place_id`가 실제 일정 활동에 들어간 결과만 통과시킨다.

#### `POST /schedules/{session_id}/required-places`

```json
{ "place_id": "sha256-place-id" }
```

- Response `200`: 선택한 장소 스냅샷
```json
{ "place_id": "sha256-place-id", "name": "A 커피집", "category": "카페", "address": "서울 ...", "map_url": "https://map.naver.com/..." }
```
- Response `404` — 현재 세션의 검색 후보 목록에 없는 장소
- Response `409` — 이미 확정된 일정

#### `DELETE /schedules/{session_id}/required-places/{place_id}`

필수 포함 제약만 해제한다. 이미 보이는 후보는 유지되며, 다음 "다시 일정 생성" 때
바뀐 제약이 반영된다.

- Response `204`

#### `GET /schedules/{session_id}/place-search`

표준 카테고리·태그 검색과 무관하게, 사용자가 입력한 이름/주소로 네이버 지역검색을
직접 호출한다(`AddCustomPlaceModal`의 "+"로 검색 후보 밖 장소를 추가할 때 사용).

- Query: `q`(검색어)
- Response `200`: `PlaceSearchResultItem[]`

#### `POST /schedules/{session_id}/required-places/custom`

`GET .../place-search` 결과 항목을 그대로 다시 보내 `is_custom=true` 필수 장소로
저장한다(세션당 최대 3개). 재생성 시 `place_candidates`에 원본 좌표로 직접 주입된다.

- Request: `PlaceSearchResultItem`과 동일한 필드(`place_id`/`name`/`category`/
  `address`/`map_url`/`mapx`/`mapy`)
- Response `200`: 저장된 장소 스냅샷
- Response `409` — 이미 3개 등록됨 또는 이미 확정된 일정

#### `POST /schedules/{session_id}/regenerate`

저장된 필수 장소 전부를 포함하는 새 후보를 만든다. 성공할 때만 기존 후보를 교체한다.
응답은 `POST /schedules`와 같으며 `required_places` 배열로 현재 고정 장소도 함께 준다.

- Request
```json
{ "api_key": "sk-ant-..." }
```
`POST /schedules`와 마찬가지로 클라이언트가 로컬 복호화한 평문.

- Response `200`
- Response `409` — 필수 장소 주변에서 시간·식사·동선 조건을 함께 만족할 수 없음.
  기존 후보는 보존된다.
- Response `422` — 필수 장소를 하나도 고르지 않음

### 후보 상세 수정 — 미리보기 후 저장

상세 화면(`CandidateDetailView`)에서 장소 교체/제외/순서 변경/시간 수정은 모두
**미리보기 → 저장** 2단계로 이뤄진다. 미리보기는 실제 반영 없이 결과만 보여주고,
저장 호출을 별도로 해야 후보가 실제로 바뀐다 — 그 사이 교통편(`selected_options`)을
바꾼 뒤 함께 저장할 수 있게 하기 위함.

#### `POST /schedules/{session_id}/candidates/{candidate_id}/preview`
장소 하나를 다른 장소로 교체하는 미리보기. 파이프라인을 실제로 호출하므로 평문
`api_key`가 필요하다.

- Request
```json
{ "excluded_place_ids": ["sha256-place-id"], "api_key": "sk-ant-..." }
```
- Response `200`
```json
{ "preview_id": "uuid", "candidate": { "...": "Candidate" } }
```

#### `POST /schedules/{session_id}/candidates/{candidate_id}/preview/{preview_id}/save`
위 미리보기를 실제 후보로 저장한다.

- Request
```json
{ "selected_options": [{ "from_order": 1, "option_id": "walk" }] }
```
- Response `200`: `Candidate`

#### `POST /schedules/{session_id}/candidates/{candidate_id}/removal/preview`
장소 하나를 빼기만 하는 미리보기(로컬 재계산만 하므로 `api_key` 불필요).

- Request
```json
{ "excluded_place_ids": ["sha256-place-id"] }
```
- Response `200`: `CandidatePreviewResponse`(위와 동일 형태)

#### `POST /schedules/{session_id}/candidates/{candidate_id}/removal/save`
- Request
```json
{ "excluded_place_ids": ["sha256-place-id"], "selected_options": [] }
```
- Response `200`: `Candidate`

#### `POST /schedules/{session_id}/candidates/{candidate_id}/reorder/preview`
활동 순서를 드래그로 바꾼 결과 미리보기.

- Request
```json
{ "ordered_positions": [2, 1, 3] }
```
- Response `200`: `Candidate`

#### `POST /schedules/{session_id}/candidates/{candidate_id}/reorder/save`
- Request
```json
{ "ordered_positions": [2, 1, 3], "selected_options": [] }
```
- Response `200`: `Candidate`

#### `POST /schedules/{session_id}/candidates/{candidate_id}/activities/time/preview`
활동 시작/종료 시각 수동 수정 미리보기. 겹치는 안 잠긴 이웃 활동은 자동으로 밀리고,
잠긴(`time_locked`) 이웃과 겹치면 `409`.

- Request
```json
{ "order": 1, "start_time": "18:30", "end_time": "20:00" }
```
- Response `200`: `Candidate`
- Response `409` — 잠긴 이웃 활동과 시간이 겹침

#### `POST /schedules/{session_id}/candidates/{candidate_id}/activities/time/save`
- Request
```json
{ "order": 1, "start_time": "18:30", "end_time": "20:00", "selected_options": [] }
```
- Response `200`: `Candidate` (해당 활동은 `time_locked: true`로 고정)

#### `POST /schedules/{session_id}/candidates/{candidate_id}/activities/{order}/unlock`
`time_locked`만 해제한다 — 시간 값 자체는 바꾸지 않는다.

- Response `200`: `Candidate`

### `POST /schedules/{session_id}/confirm`
후보 하나를 최종 확정 (`status: confirmed`)하고, 동시에 공유 링크(slug)를 발급한다 —
별도 "링크 생성" 호출 없이 이 응답의 `share_slug`를 그대로 공유 URL에 쓴다.

- Request
```json
{
  "candidate_id": "A",
  "selected_options": [
    { "from_order": 1, "option_id": "walk" }
  ]
}
```
`selected_options`는 사용자가 후보 상세 화면에서 구간별로 고른 교통편(`option_id`,
`POST .../routes` 응답의 `routes[].options[].option_id` 중 하나)이다. 비어있으면(예:
아직 경로를 안 골랐거나 예전 클라이언트) 서버가 계산해둔 `recommended_option_id`
선택을 그대로 둔다. 값이 있으면 확정 시점에 후보의 저장된 `routes[].selected_option_id`에
반영되고, 그 값이 `GET /share/{slug}` 응답에도 그대로 노출된다 — 공유 화면이
추천값이 아니라 사용자가 실제로 고른 교통편을 보여줘야 하기 때문.
- Response `200`
```json
{ "session_id": "uuid", "status": "confirmed", "share_slug": "aB3xK9pL" }
```
- Response `409` — 이미 확정된 세션(draft→confirmed는 한 방향만 허용)
- Response `404` — 존재하지 않는 일정 또는 후보

## 5. 공유

확정(`confirm`) 시 `share_slug`가 함께 발급되므로 별도 "링크 생성" 엔드포인트는 없다.

### `GET /share/{slug}`
공개 조회. **인증 불필요.**

응답은 `POST .../confirm`으로 확정된 `Candidate` 하나 그대로다(계정 정보/원본
입력/피드백 대화/다른 후보 2개는 제외) — `routes[].selected_option_id`는 사용자가
확정 시점에 구간별로 실제로 골랐던 교통편을 반영한다(`POST .../confirm`의
`selected_options` 참고).

- Response `200`
```json
{
  "candidate_id": "A",
  "title": "실내 위주 알뜰 코스",
  "why_recommended": "예산 내에서 보드게임과 파스타를 모두 포함",
  "activities": [ "... (POST /schedules 응답과 동일 구조)" ],
  "routes": [
    {
      "from_order": 1,
      "to_order": 2,
      "recommended_option_id": "transit-0",
      "selected_option_id": "walk",
      "options": [
        { "option_id": "walk", "mode": "walk", "duration_minutes": 15, "fare_krw": 0, "transfer_count": 0, "description": "", "path": [] },
        { "option_id": "transit-0", "mode": "transit", "duration_minutes": 8, "fare_krw": 1400, "transfer_count": 0, "description": "지하철 강남 → 교대", "path": [[37.5, 127.0], [37.6, 127.1]] }
      ]
    }
  ],
  "feasibility_warning": null
}
```
- Response `404` — 존재하지 않는 링크

### `GET /public-share-links/{session_id}/candidates/{candidate_id}`
확정 직후 남는 소유자 형식 URL(`/schedules/{id}/candidates/{id}/share`)을 공개
`/share/{slug}` 주소로 변환한다. URL의 후보가 실제 확정 후보와 정확히 일치할 때만
slug를 반환하며, 초안·다른 후보·존재하지 않는 세션은 모두 같은 `404`로 처리해
비공개 일정의 존재 여부를 노출하지 않는다.

- 인증: 불필요
- Response `200`
```json
{ "slug": "aB3xK9pL" }
```
- Response `404` — 존재하지 않는 링크(비공개 일정 포함)

## 6. 에러 코드 요약

| 코드 | 의미 |
|---|---|
| 400 | 잘못된 요청 (형식 오류, 키 검증 실패 등) |
| 401 | 인증 필요/토큰 만료 |
| 403 | 권한 없음 (타인 리소스 접근) |
| 404 | 리소스 없음 |
| 409 | 조건 충돌로 처리 불가 (일정 생성/수정 불가) |
| 422 | 요청 바디 검증 실패 (필수 필드 누락 등, FastAPI 기본 처리) |
| 502 | 외부 API(네이버 지역검색 등) 호출 실패 |

## 7. 스킵한 것 → 필요해지면 추가
- 일정 목록 페이지네이션(`GET /confirmed-schedules`/`GET /draft-schedules`는 이미
  구현됐으나 전체 목록을 한 번에 반환 — 개수가 많아지면 추가)
- Rate limiting → 트래픽/어뷰징 문제가 실제로 확인되면
