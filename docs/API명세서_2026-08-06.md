|---|---|

## 1. 인증

### `POST /auth/google`
Google id_token을 검증하고 자체 세션 JWT를 발급한다.

- 인증: 불필요
- Request
```json
{ "id_token": "eyJhbGciOi..." }
```
- Response `200`
```json
{
  "access_token": "eyJhbGciOi...",
  "token_type": "bearer",
  "user": {
    "id": "uuid",
    "email": "user@example.com",
    "name": "홍길동"
  }
}
```
- Response `401` — id_token 검증 실패

### `GET /me`
현재 로그인 사용자 정보 조회.

- Response `200`: 위 `user` 객체와 동일
- Response `401` — 토큰 없음/만료

## 2. API 키 (BYOK)

### `POST /me/llm-credential`
사용자가 선택한 AI 제공자(Claude 또는 GPT)의 API 키를 등록한다. 저장 전 짧은 검증 호출을 1회 수행한다. 이미 등록된 키가 있으면 교체(제공자 포함)된다.

- Request
```json
{ "provider": "anthropic", "api_key": "sk-ant-..." }
```
`provider`는 `anthropic`(Claude) 또는 `openai`(GPT) 중 하나.
- Response `201`
```json
{ "provider": "anthropic", "verified_at": "2026-08-06T10:00:00Z" }
```
- Response `400` — 키 검증 실패 (`{"detail": "API 키가 유효하지 않습니다."}`) 또는 `provider` 값이 허용 범위 밖인 경우

### `DELETE /me/llm-credential`
등록된 키 삭제.

- Response `204`

### `GET /me/llm-credential`
등록 여부/상태만 확인 (키 원문은 절대 반환하지 않음).

- Response `200`
```json
{ "registered": true, "provider": "anthropic", "verified_at": "2026-08-06T10:00:00Z" }
```

## 3. 일정 생성 · 조회

### `POST /schedules`
조건을 입력받아 Step1(조건 정규화) → Step2(후보 생성) → Step3(검증·병합)까지
실행하고, **경로(routes) 없는** 3개 후보를 반환한다. 경로는 사용자가 후보 하나를
고른 뒤 `POST /schedules/{session_id}/routes`로 별도 조회한다(2026-08-10 파이프라인
순서 재설계 — `docs/AI파이프라인_Step별_설계_2026-08-09.md` "전체 흐름" 참고,
ODsay 호출 비용을 실제로 열어볼 후보 1개로만 제한하기 위함).

- Request

`liked_text`/`disliked_text`는 태그 선택이 아니라 자유 텍스트 그대로 받는다(각 최대
100자). Step1 조건 정규화(LLM)가 여기서 구조화 태그(`NormalizedConditions.liked_tags`
등)를 뽑아낸다 — 기술설계 §4 Step1.

`regions`는 최대 3개까지 배열로 받는다. 그중 세부지역 없이 시/도만인 항목은
최대 1개까지만 허용된다(예: `["서울", "경기 수원", "경기 용인"]`은 가능,
`["서울", "경기"]`는 불가). 포함관계 중복 제거(예: "서울"과 "서울 잠실"을 같이
보내면 "서울 잠실" 제거)와 개수 제한은 프런트에서 먼저 걸러주고, 백엔드
`NormalizedConditions.validate_regions()`가 다시 검증한다(기술설계 §4 Step1 참고).

```json
{
  "purpose": "date",
  "headcount": 2,
  "time_range": ["2026-08-15T10:00:00", "2026-08-15T21:00:00"],
  "regions": ["서울 강남"],
  "liked_text": "날씨가 너무 더워서 실내 위주로, 콩국수나 텐동을 점심으로 먹고 싶어",
  "disliked_text": "해산물은 못 먹어요",
  "budget_per_person": 50000
}
```
- Response `200`
```json
{
  "session_id": "uuid",
  "candidates": [
    {
      "candidate_id": "A",
      "title": "실내 위주 알뜰 코스",
      "why_recommended": "예산 내에서 보드게임과 파스타를 모두 포함",
      "activities": [
        {
          "order": 1,
          "name": "OO파스타",
          "category": "식당",
          "address": "서울 강남구 ...",
          "start_time": "18:00",
          "end_time": "19:30",
          "price_range_per_person": [15000, 20000],
          "operating_hours": "11:00-22:00",
          "phone": "02-...",
          "info_needs_check": false
        }
      ],
      "routes": [],
      "feasibility_warning": null
    }
  ]
}
```
- Response `422` — 필수 조건 누락 (조건 정규화 단계 실패)
- Response `409` — 조건을 만족하는 일정을 만들 수 없음
```json
{
  "detail": "예산 조건으로 일정을 만들 수 없습니다.",
  "reason": "선택하신 지역·시간대의 활동 비용이 예산을 초과합니다.",
  "adjustable_conditions": ["budget_per_person", "regions"]
}
```

### `POST /schedules/{session_id}/routes`
사용자가 3개 후보 중 하나를 고르면, 그 후보에 한해 Step4(`enrich_routes`)를 실행해
구간별 이동 옵션을 채운 최종 1안을 반환한다(엔드포인트 이름·형태는 가칭 — 라우터
구현 시 확정). `car` 모드는 프로바이더 미정으로 보류라 항상 빠진다(스키마는
`Literal["walk","transit","car"]` 유지, 나중에 카카오모빌리티 연동 시 값만 채움).

- Request
```json
{ "candidate_id": "A" }
```
- Response `200`
```json
{
  "candidate_id": "A",
  "activities": [ /* Step4가 실제 이동시간 기준으로 재조정한 start_time/end_time 포함 */ ],
  "routes": [
    {
      "from_order": 1,
      "to_order": 2,
      "recommended_mode": "transit",
      "options": [
        { "mode": "walk", "duration_minutes": 15, "fare_krw": 0 },
        { "mode": "transit", "duration_minutes": 8, "fare_krw": 1400 }
      ]
    }
  ],
  "feasibility_warning": null
}
```

### `GET /schedules/{session_id}`
저장된 일정 세션 조회 (본인 소유만).

- Response `200`: `POST /schedules` 응답과 동일한 `candidates` 포함 — `POST
  .../routes`를 아직 안 불렀으면 `routes`는 빈 배열
- Response `403` — 타인 소유 세션
- Response `404` — 존재하지 않음

## 4. 일정 수정 · 피드백

### `POST /schedules/{session_id}/feedback`
선택한 후보에 대한 피드백을 반영해 일정을 수정하거나 재생성한다.

- Request
```json
{
  "candidate_id": "A",
  "feedback_type": "text",
  "content": "예산을 1만원 정도 늘리고, 실내 활동으로 하나 바꿔줘"
}
```
- Response `200`: 수정된 단일 후보 또는 새 후보 목록 (`POST /schedules` 응답과 동일 구조)
- Response `409` — 반영 불가
```json
{
  "detail": "요청하신 조건으로는 반영이 어렵습니다.",
  "reason": "해당 예산으로는 실내 활동 대체가 불가능합니다.",
  "adjustable_conditions": ["budget_per_person", "time_range"]
}
```

### `POST /schedules/{session_id}/confirm`
후보 하나를 최종 확정 (`status: confirmed`).

- Request
```json
{ "candidate_id": "A" }
```
- Response `200`
```json
{ "session_id": "uuid", "status": "confirmed" }
```

## 5. 공유

### `POST /schedules/{session_id}/share`
확정된 일정의 공개 공유 링크 생성.

- Response `201`
```json
{ "slug": "aB3xK9pL", "share_url": "https://모두약속.app/share/aB3xK9pL" }
```
- Response `400` — 아직 확정(`confirm`)되지 않은 일정

### `GET /share/{slug}`
공개 조회. **인증 불필요.**

- Response `200`
```json
{
  "title": "실내 위주 알뜰 코스",
  "activities": [ "... (계정 정보/원본 입력/피드백 대화 제외)" ],
  "routes": [ "..." ]
}
```
- Response `404` — 존재하지 않는 링크

## 6. 에러 코드 요약

| 코드 | 의미 |
|---|---|
| 400 | 잘못된 요청 (형식 오류, 키 검증 실패 등) |
| 401 | 인증 필요/토큰 만료 |
| 403 | 권한 없음 (타인 리소스 접근) |
| 404 | 리소스 없음 |
| 409 | 조건 충돌로 처리 불가 (일정 생성/수정 불가) |
| 422 | 요청 바디 검증 실패 (필수 필드 누락 등, FastAPI 기본 처리) |

## 7. 스킵한 것 → 필요해지면 추가
- 일정 목록 조회(`GET /schedules`, 페이지네이션) → "내 일정 히스토리" 화면이 실제로 필요해지면
- Rate limiting → 트래픽/어뷰징 문제가 실제로 확인되면
