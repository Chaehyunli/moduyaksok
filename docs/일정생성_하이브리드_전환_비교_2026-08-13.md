# 일정 생성 AI·알고리즘 하이브리드 전환 비교

## 결론

일정의 장소·순서·식사·필수 포함·후보 간 중복은 알고리즘이 결정하고, AI는 자연어
요구 해석, 검색 데이터로 확인할 수 없는 소프트 취향 점수, 제목과 추천 설명만 맡기는
구조로 전환한다. 사용자의 요구를 잘 지키는 것과 서로 다른 세 일정을 주는 것을 동시에
달성하려면 이 역할 분리가 가장 안전하다.

이전 방식은 AI가 세 관점의 장소를 각각 독립적으로 골랐다. 후보 하나만 보면 자연스러울
수 있지만 세 호출이 같은 인기 장소로 수렴하고, 잘못 만든 후보를 Step3에서 버린 뒤 다시
호출하는 구조라 후보 수와 수정 결과가 흔들렸다. 전환 방식은 유효한 조합을 먼저 여러 개
만들고 세 후보를 한 세트로 평가해 장소와 카테고리 겹침을 함께 줄인다.

## 적용된 역할 분담

| 단계 | 전환 전 | 전환 후 |
|---|---|---|
| 자연어 조건 | LOW AI가 태그·식사 여부 추출 | LOW AI가 태그·식사 여부·의미 축·우선순위 추출 |
| 장소 검색 | 네이버 카테고리·태그 검색 | 동일. 검색 결과마다 안정적인 `place_id` 추가 |
| 검색 가능한 조건 | AI 프롬프트 지시 후 Step3 사후 검증 | 생성 풀 필터와 Beam 상태의 하드 조건 |
| 주관적 조건 | 세 Step2 AI가 각자 해석 | 소프트 조건이 있을 때만 MID AI 1회가 장소 전체를 약하게 점수화 |
| 장소 선택 | 관점별 MID AI 최대 3회 | 알고리즘 Beam Search |
| 후보 다양성 | 세 AI 호출의 독립성에 기대고 사후 유사도 안내 | 여러 유효 조합 중 세 후보를 공동 선택 |
| 시간 배정 | 결정론적 계산 | 결정론적 계산 유지 |
| 최종 판단 | HIGH AI가 후보를 추가로 드롭 가능 | 규칙만 드롭 가능. AI는 제목·설명 편집만 담당 |
| 이동 경로 | 선택한 후보만 외부 길찾기 조회 | 동일 |

## 생성 시 보장되는 조건

전환 생성기는 아래 조건을 후보를 완성한 뒤 검사하는 데 그치지 않고, 후보를 확장하는
도중부터 지킨다.

1. 검색 결과에 없는 장소를 만들지 않는다. 모든 장소는 안정적인 `place_id`를 가진다.
2. 사용자가 필수로 고른 장소는 모두 seed로 시작하며 빠질 수 없다.
3. 사용자가 같은 태그의 장소를 여러 개 필수로 고른 경우 그 개수까지 허용한다.
4. 필수가 아닌 장소가 이미 충족한 좋아요 태그를 다시 중복 소비하지 못한다.
5. 점심·저녁이 포함된 시간 범위에서는 필요한 수만큼 식사 장소를 선택한다.
6. 검색 가능한 비선호가 제목·카테고리·태그 검색 근거에 명백히 나타난 일반 장소는
   생성 풀에서 제외한다. 사용자가 그 장소를 직접 필수로 고른 경우에는 명시적 선택을
   우선하고 경고 가능한 일정으로 유지한다.
7. 일반 장소끼리의 과도한 이동은 확장 단계에서 막는다. 멀리 떨어진 필수 장소는
   삭제하지 않고 이동 경고와 실제 교통편 계산 대상으로 남긴다.
8. 가격은 실제 메뉴 가격이 아니므로 약한 정렬 신호로만 쓰고 추정 범위로 표시한다.

## 다양성을 만드는 방식

한 후보씩 차례로 만들고 이전 후보의 장소만 피하는 방식은 쉽게 지역 최적점에 갇힌다.
전환 방식은 각 생활권·태그 앵커 계획에서 여러 완성 조합을 만든 다음, 세 후보의 조합을
동시에 평가한다.

공동 평가에는 다음 항목이 들어간다.

- 필수 장소를 제외한 장소 ID Jaccard 겹침
- 카테고리 집합 Jaccard 겹침
- `식사 → 카페 → 활동`처럼 카테고리 순서가 완전히 같은지
- 좋아요 태그의 우선순위와 새 태그 충족 수
- 후보 내부의 카테고리 다양성
- 이동시간과 가격 하한 추정치
- 소프트 취향의 약한 가감점

세 결과의 성격은 동일한 점수식 복제가 아니라 가성비, 동선, 취향·경험 다양성 쪽의
가중치를 다르게 둔다. 다만 세 후보 모두 같은 하드 조건을 통과하므로 특정 관점이라는
이유로 필수 요구를 어기지는 않는다.

## 일정 수정 기능 비교

### 필수 장소를 추가하거나 해제한 뒤 전체 재생성

전환 전에는 세 AI가 필수 장소를 프롬프트로 받아 각각 다시 선택했고, 누락은 Step3가
사후에 막았다. 필수가 멀리 떨어져 있거나 같은 태그에 여러 개면 클러스터·이동 필터와
충돌해 후보가 전멸할 가능성이 컸다.

전환 후에는 모든 필수 장소를 먼저 고정한 뒤 각 필수 주변의 일반 후보 합집합으로 빈
자리를 채운다. 필수 장소끼리 2.5km를 넘거나 좌표가 없다는 이유로 계획 자체를 없애지
않는다. 필수 장소가 바뀌면 현재 저장 조건의 `required_place_ids`를 기준으로 세 후보를
다시 공동 생성한다.

### 상세에서 장소 하나 제외 후 저장만 하기

장소를 빼는 순간 미리보기 후보에서는 해당 활동만 제거하고 남은 활동의 순서를 다시
매긴다. 앞뒤가 새로 붙는 구간의 교통편도 미리보기 기준으로 다시 계산한다. 저장을 누를
때만 후보와 제외 ID를 영속화하므로, 저장 전 목록 이동이나 새로고침은 원본으로 돌아가고
저장 후에는 목록과 새로고침 모두 변경본을 읽는다. 일정 개수를 줄이는 선택이므로 생성
알고리즘은 부르지 않는다.

### 상세에서 장소 하나 제외 후 대체 장소 채우기

전환 전에는 남은 장소를 AI 프롬프트에 고정 목록으로 넣고 새 장소를 하나 요청한 뒤
사후 검사했다. AI가 남은 장소를 누락하거나 두 곳을 바꾸면 실패했다.

전환 후에는 남은 장소의 ID 전체가 Beam seed다. 목표 개수를 `남은 개수 + 1`로 고정해
정확히 한 장소만 추가한다. 생성된 순서로 전체 시간을 다시 배정하고, 새로 맞닿은 모든
구간의 교통편을 다시 조회한다. 다른 후보 A/B/C의 제외 목록과 내용은 건드리지 않는다.

### 후보별 제외 조건을 반영한 전체 재생성

각 후보의 제외 ID는 독립된 풀에 적용한다. A에서 뺀 장소가 B에서 자동으로 빠지지는
않는다. A, B, C를 다시 만들 때 이미 앞 후보에서 사용한 비필수 장소는 다음 후보 풀에서
우선 제외해 중복을 줄이고, 그 때문에 후보를 만들 수 없을 때만 원래 후보별 풀로
폴백한다. 필수 장소는 세 후보에서 공통이어도 다양성 벌점 대상이 아니다.

## 여러 관점의 전환 전후 비교

| 관점 | 전환 전 | 전환 후 | 판단 |
|---|---|---|---|
| 요구 충족 | 프롬프트 준수 후 사후 드롭 | 생성 중 불변조건 | 전환 후가 안정적 |
| 후보 수 | Step3 AI 판단과 재시도로 1~3개 변동 | 규칙상 유효하면 AI가 줄이지 않음 | 전환 후가 예측 가능 |
| 장소 다양성 | 독립 AI가 같은 상위 장소로 수렴 | 세 후보 공동 최적화 | 전환 후가 유리 |
| 구조 다양성 | 장소가 달라도 카테고리 흐름이 같을 수 있음 | 카테고리 집합과 순서도 벌점 | 전환 후가 유리 |
| 필수 다중 선택 | 거리·식사·태그 필터와 충돌 가능 | 필수 우선, 일반 제약은 경고로 완화 | 전환 후가 유리 |
| 장소 제외 수정 | AI가 고정 장소를 다시 해석 | 남은 ID를 코드가 고정 | 전환 후가 정확 |
| 설명 자연스러움 | AI가 장소 선택과 설명을 함께 수행 | AI가 검증된 결과의 설명에 집중 | 전환 후가 같거나 유리 |
| 결정 재현성 | 호출마다 결과 변동 | 같은 풀·조건이면 선택은 결정론적 | 전환 후가 유리 |
| 장애 격리 | Step2 AI 실패가 후보 생성 실패 | 소프트 점수 실패는 0점 폴백 | 전환 후가 유리 |
| 비용·지연 | 일반 5회, 재시도 시 추가 호출 | 소프트 없음 2회, 있음 3회 | 전환 후가 유리 |
| 디버깅 | 왜 AI가 골랐는지 역추적 어려움 | 필터·점수·고정 ID로 원인 분리 가능 | 전환 후가 유리 |
| 데이터 한계 | AI가 가격·분위기를 그럴듯하게 추정할 위험 | 가격은 약한 추정, 분위기는 낮은 확신 | 전환 후가 정직 |

호출 수는 일반적인 1회 생성 기준이다. 전환 전은 Step1 LOW 1회 + Step2 MID 3회 +
Step3 HIGH 1회다. 전환 후는 Step1 LOW 1회 + Step3 HIGH 1회이며, 검색 데이터로 알 수
없는 소프트 선호가 있을 때만 MID 배치 점수 1회가 추가된다. Upstage는 현재 세 티어가
모두 `solar-pro4`를 가리키지만, 역할과 호출 수 분리는 다른 provider 및 향후 모델 변경에
그대로 의미가 있다.

## 수치 해석

2026-08-12의 동일 Upstage 골든 입력 1회 실험에서는 기존 Step2가 MID 6회,
입력/출력 7,575/2,297 토큰, 약 11.96초였고 당시 Beam 프로토타입의 소프트 배치가
MID 1회, 506/265 토큰, 약 2.15초였다. 이 값은 한 번의 실험이라 품질 우위를
확정하는 수치가 아니라 호출 구조의 비용·속도 가능성만 보여준다.

2026-08-13 새 결정론적 회귀 fixture에서는 후보마다 5개 장소, 점심·저녁 2곳,
좋아요 태그 중복 0, 필수 태그 누락 0이었다. 세 후보의 장소 Jaccard는
`0.000 / 0.111 / 0.000`, 카테고리 Jaccard는 `0.250 / 0.667 / 0.250`이었다.
이는 실제 네이버 검색 품질을 측정한 운영 수치가 아니라 알고리즘 불변조건과 공동 선택이
작동하는지 보는 합성 fixture 결과다. 이전 문서의 프로토타입 관측치 0.87→0.30과도
직접적인 동등 비교를 하면 안 된다.

## 현재 안전장치와 전환 방법

기본값은 `SCHEDULE_GENERATOR_MODE=hybrid`다. 문제가 발견되면 환경변수를
`legacy`로 바꿔 최초 생성과 전체 재생성의 기존 AI 경로로 즉시 되돌릴 수 있다.
장소 상세에서 남은 장소를 고정하고 한 자리만 교체하는 경로는 데이터 무결성이 더 중요한
수정 작업이라 하이브리드 생성기를 사용한다.

최종 전환 판단은 실제 저장 장소 풀을 익명 fixture로 고정하고 아래 지표를 같은 입력으로
반복 측정해야 한다.

- 세 후보 생성 성공률과 후보당 장소 수
- 필수 장소·식사 슬롯·좋아요 최소 충족률
- 환각·동일 장소·동일 태그·비선호 위반 수
- 후보 간 장소·카테고리 Jaccard와 카테고리 시퀀스 중복률
- 평균·최대 구간 이동시간과 필수 때문에 발생한 경고 수
- 장소 제거 후 다른 장소 보존률과 정확히 한 자리 대체 성공률
- 호출 수, 입력·출력 토큰, 비용, p50/p95 지연
- 사용자가 실제로 고른 후보와 이후 제거한 장소 비율

특히 마지막 두 사용자 행동 지표가 중요하다. 자동 지표상 다양해도 사용자가 세 후보 모두
마음에 들지 않아 계속 장소를 빼면 좋은 생성기가 아니다. 반대로 카테고리 일부가 겹쳐도
선택률이 높고 수정 횟수가 적다면 실제 제품 품질은 더 좋다.

## 남아 있는 한계

- 네이버 장소 검색에 메뉴 가격·영업시간·실시간 혼잡도가 없으므로 정확히 보장할 수 없다.
- 문자열 기반 검색 가능한 비선호 필터는 `해산물`과 `횟집` 같은 의미 동의어를 모두
  알아내지 못한다. 검색 단계의 비선호 태그 쿼리가 1차 방어이고, 동의어 사전 또는 장소
  상세 데이터가 생기면 강화해야 한다.
- 다양성을 높이면 이동거리가 늘 수 있다. 일반 구간 15분 상한 안에서만 다양성을
  최적화하지만, 실제 도로·대중교통 시간은 후보 상세 진입 후 다시 계산된다.
- 실제 운영 장소 풀을 사용한 legacy/hybrid 반복 A/B 평가는 아직 실행하지 않았다.
  API 비용이 드는 평가는 키가 있는 개발 환경에서 동일 fixture·동일 provider로 별도
  실행하고 결과를 이 문서에 누적해야 한다.
