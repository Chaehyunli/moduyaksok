# 일정 생성·수정 성능 측정 보고서

- 측정일: 2026-08-13
- 측정 환경: 로컬 FastAPI + 로컬 PostgreSQL/Redis + 실제 Upstage/Naver/ODsay/NCP API
- LLM provider/model: Upstage `solar-pro4`
- 측정 방식: 실제 HTTP 엔드포인트를 순서대로 호출한 1회 종단 사이클
- 주의: 1회 표본이므로 평균이나 SLA가 아니라 현재 구조의 대표 관측값이다.

## 1. 측정 시나리오

입력 조건:

- 지역: 경기 수원
- 시간: 10:00~21:00
- 목적/인원: 데이트, 2명
- 좋아요: 와플, 일식 초밥
- 싫어요: 해산물
- 1인 예산: 50,000원

실행 순서:

1. 초기 일정 후보 3개 생성
2. 생성 후보의 좋아요 검색 장소 1곳을 필수 장소로 등록하고 후보 3개 재생성
3. 재생성된 후보에서 비필수·비태그 장소 1곳을 제거하고 대체 장소 및 이동 경로 생성

측정으로 생성한 일정 세션은 완료 후 DB에서 삭제했다.

## 2. 작업별 결과

| 작업 | 총 소요시간 | HTTP 결과 | 결과 |
|---|---:|---:|---|
| 초기 일정 생성 | 9.494초 | 200 | 후보 3개, 장소 풀 92곳 |
| 필수 장소 추가·재생성 | 6.680초 | 200 | 후보 3개 |
| 기존 장소 제거·대체 | 10.898초 | 200 | 활동 5개, 이동 구간 4개 |
| 전체 사이클 | **27.072초** | 모두 성공 | 생성→필수 수정→대체 수정 완주 |

필수 장소 등록 자체는 0.038초였고, 나머지 6.642초가 실제 재생성 요청이었다.

## 3. Step별 결과

### 3.1 초기 일정 생성

| Step | 소요시간 | 전체 초기 생성 대비 | 설명 |
|---|---:|---:|---|
| Step 1: 입력 정규화 LLM | 4.509초 | 47.5% | 자유 텍스트에서 좋아요·싫어요 태그 추출 |
| 네이버 장소 검색 | 1.206초 | 12.7% | 21개 질의, 고유 장소 92곳 |
| 알고리즘 생성 및 전후 처리 | 약 0.394초 | 4.2% | 장소 조합·순서·시간·하드 규칙 처리 |
| Step 3: 검증 설명 LLM | 3.271초 | 34.5% | 후보 제목·추천 이유·경고 생성 |
| HTTP/DB 등 나머지 | 약 0.114초 | 1.2% | 직렬화 및 저장 포함 |
| 합계 | **9.494초** | 100% | |

초기 생성 시간의 약 82%가 두 번의 LLM 호출이었다. 장소 검색과 일정 알고리즘 자체는 합쳐 약 1.6초였다.

### 3.2 필수 장소 추가·재생성

| Step | 소요시간 | 설명 |
|---|---:|---|
| 필수 장소 DB 등록 | 0.038초 | 필수 제약 저장 |
| 알고리즘 생성 및 전후 처리 | 약 0.233초 | 저장된 장소 풀 재사용, 필수 장소 포함 조합 생성 |
| Step 3: 검증 설명 LLM | 6.284초 | 후보 3개 설명 생성 |
| DB 저장 및 HTTP 처리 | 약 0.125초 | 후보 교체 및 응답 |
| 합계 | **6.680초** | |

필수 재생성 시간의 약 94%가 Step 3 LLM 호출이었다. 네이버 검색과 Step 1은 다시 실행하지 않았다.

### 3.3 기존 장소 제거·대체

| Step | 소요시간 | 설명 |
|---|---:|---|
| 대체 장소 알고리즘 | 0.049초 | 기존 장소 유지 및 대체 장소 1곳 선정 |
| Step 3: 검증 설명 LLM | 10.125초 | 변경 후보 설명 생성 |
| 이동 경로 보강 | 0.613초 | 4개 구간, ODsay와 NCP Maps 병렬 조회 |
| 나머지 처리 | 약 0.111초 | 슬롯 시간 복원, 미리보기 저장, HTTP 처리 |
| 합계 | **10.898초** | |

대체 수정 시간의 약 93%가 Step 3 LLM 호출이었다. 장소를 고르는 알고리즘은 0.05초 미만이었다.

## 4. 이전 로직과 비교

### 속도와 안정성

현재 구조가 명확히 더 좋다.

| 항목 | 이전 | 현재 |
|---|---|---|
| LLM 제한시간 | 최초에는 명시적 제한 없음. 중간 수정안은 60초 | 20초 |
| SDK 자동 재시도 | 기본 2회 | 0회 |
| LLM 최악 대기 | 중간 수정안 기준 약 180초, 최초 측정에서는 20분 이상 정체 관찰 | 호출당 약 20초 상한 후 폴백 |
| 네이버 검색 | 예시 조건 36회 | 21회 |
| 경로 API | 구간 간 병렬, 구간 안에서 ODsay→NCP 순차 | 구간 간 및 provider 간 모두 병렬 |
| Step 3 실패 | 요청 전체 실패 가능 | 규칙을 통과한 일정과 기본 설명으로 폴백 |
| 관측 가능성 | 토큰 로그 위주 | 각 Step·검색·경로·LLM 소요시간 기록 |

이전 5회 측정은 세 번째 초기 생성 중 외부 응답이 장시간 멈춰 약 20분 후 중단되어, 동일 조건의 완주 수치가 없다. 따라서 “몇 배 빨라졌다”는 정확한 비율은 계산할 수 없다. 다만 이전에는 한 요청이 2~3분 또는 그 이상 멈출 수 있었고, 현재 완주 사이클에서는 가장 긴 단일 작업이 10.898초였다.

### 일정 품질과 기능 정확성

기능 정확성은 개선됐다.

- 필수 식사 장소가 점심·저녁 슬롯에 배치된다.
- 같은 좋아요 태그의 기존 장소는 필수 장소로 교체된다.
- 좋아요 태그를 최소 절반 이상 반영하는 규칙이 생성과 검증에 동일하게 적용된다.
- 미반영 필수 장소 때문에 대체 일정이 6곳을 요구하던 오류가 제거됐다.
- 경로 provider 하나의 비정상 응답이 전체 대체 요청을 500으로 만들지 않고 해당 교통수단만 생략한다.

다만 추천 품질이 이전보다 반드시 더 좋다고 단정할 수는 없다. 일반 카테고리 검색을 두 정렬에서 한 정렬로 줄여 장소 풀이 기존 화면의 133곳에서 이번 측정 92곳으로 약 31% 감소했다. 좋아요·싫어요 태그 검색은 두 정렬을 유지하므로 핵심 선호 정확도는 보존했지만, 후보 다양성 영향은 별도의 다회 품질 평가가 필요하다. Step 3 LLM은 유지되므로 정상 응답 시 제목·추천 이유 품질은 기존 방식과 같다.

## 5. 관찰된 변동성

현재 구조에서도 외부 LLM 응답시간 변동이 크다. 최종 완주 전 관찰된 동일 계열 요청에서는:

- 초기 생성: 9.49초, 14.92초, 30.29초
- 필수 재생성: 6.68초, 6.88초, 9.90초
- 대체 Step 3 LLM: 10.13초, 다른 시도에서는 16.01초

첫 초기 생성의 Step 1 LLM은 한 번 22.15초가 걸렸다. SDK의 20초 timeout은 네트워크 연결·응답 파싱 경계를 포함한 정확한 wall-clock 강제 종료가 아니어서 몇 초 초과할 수 있다. 그래도 자동 재시도를 제거했기 때문에 이전처럼 같은 호출이 반복되어 수분으로 늘어나지는 않는다.

## 6. 결론

- 현재 구조는 이전보다 속도와 장애 복원력 측면에서 확실히 개선됐다.
- 최종 1회 완주 기준 전체 편집 사이클은 27.07초였다.
- 실제 일정 조합 알고리즘은 0.05~0.4초 수준이며 병목이 아니다.
- 현재 지연의 절대적인 병목은 유지하기로 한 Step 3 Upstage LLM이다.
- 초기 생성에서는 Step 1과 Step 3, 수정 요청에서는 Step 3가 대부분의 시간을 차지한다.
- 추천 품질 저하 여부는 이번 1회 속도 측정만으로 판단할 수 없다. 최소 5회 지연 측정과 고정 골든셋 품질 평가를 함께 수행해야 결론을 낼 수 있다.

권장 다음 측정은 같은 입력을 5회 반복해 평균·중앙값·최댓값을 구하고, 각 결과의 후보 수·좋아요 반영률·장소 중복률도 함께 기록하는 것이다.
