# AI 파이프라인 Step별 상세 설계

`docs/기술설계_2026-08-06.md` §4(거시 설계)와 `moduyaksok-backend/CLAUDE.md`(결정 배경), 각
`app/pipeline/*_step*.py`의 docstring(구현 세부)에 흩어져 있던 "이 Step을 왜 이렇게
설계했는지"를 Step별로 모아 정리한 문서. 스키마 자체(필드명, 타입)는
`app/pipeline/schemas.py`가 원본이니 여기서는 "왜"에 집중한다.

## 전체 흐름

**Step1 → Step2 → Step3 → Step4 순서**(2026-08-10 재설계 — 원래는 이동 동선 보강이
검증·병합보다 먼저였는데, 실행 순서에 맞춰 두 단계의 번호 자체를 스왑했다: 검증·
병합이 Step3, 이동 동선 보강이 Step4. 파일명도 `synthesize_step4.py` →
`synthesize_step3.py`, `enrich_step3.py` → `enrich_step4.py`로 변경). 사용자가
UI에서 후보를 직접 고른 뒤에야 경로(Step4)를 조회하는 흐름이라, 파이프라인이
하나의 요청 생명주기가 아니라 **두 단계로 나뉜 요청**이 됐다:

1. `POST /schedules`(가칭): Step1 → Step2 → Step3까지 실행해 장소·시간이 확정되고
   검증까지 끝난 후보 3개(경로 없음)를 반환한다.
2. 사용자가 3개 중 하나를 선택 → 그 후보 1개에 한해 별도 엔드포인트(가칭
   `POST /schedules/{id}/routes`, 라우터 설계 시 확정할 것)가 Step4를 실행해 구간별
   이동 옵션을 채운다.

**왜 이 순서인가(2026-08-10 결정)**: Step3(검증·병합)가 실제로 필요로 하는 건
Step2의 장소·시간 데이터뿐이고(환각/시간겹침/예산초과 검증, 유사도 검사,
`why_recommended` 생성 — 경로 데이터 불필요) Step4(ODsay 호출)만 후보마다 비용이
든다. 기존 순서대로면 사용자가 결국 1개만 볼 3개 후보 전부에 대해 구간별 ODsay를
미리 호출하는 낭비가 생긴다(ODsay Basic 등급이 일 1,000건 한도라 특히 아까움) —
Step4를 선택 이후로 미루면 실제로 열어볼 후보 1개분의 호출만 나간다.

**DB 저장 지점이 하나에서 둘로 늘어남(TODO, 라우터 구현 시 확정)**: 기존엔 "최종
결과만 DB에 저장하고 그 전 중간 산출물은 요청 하나의 생명주기 동안 메모리에만
존재"라고 설계했는데, 이제 두 요청 사이에 경로 없는 후보 3개를 어딘가에 들고 있어야
한다. `schedule_session` 테이블에 Step3 직후 상태(경로 없는 3개 후보)를 저장하고,
Step4 완료 시 그 레코드를 갱신하는 쪽이 지금 스키마(`candidates` JSONB 1컬럼)와
가장 맞을 걸로 보이나, 실제 라우터/ERD 작업 시 다시 판단할 것.

오케스트레이션 프레임워크(LangGraph 등) 없이 plain async 함수 체인으로 구성한다.
병렬화 지점은 **Step2 내부의 관점 3개 fan-out**과 **Step4 내부의 구간별 옵션 조회**
두 곳이다.

파이프라인 오류/타임아웃 공통 정책(§4): 각 LLM 호출에 개별 timeout을 걸고, 개별
실패는 스킵하고 나머지로 진행 — 완전 실패는 관련된 호출이 전부 실패했을 때만.
프런트 로딩 UX는 MVP 기준 스트리밍(SSE) 없이 단순 로딩 스피너 + 동기 응답(§4, §7).

## Step1 — 조건 정규화 (`normalize_conditions`) — **구현 완료**

**목적**: 사용자가 자유 텍스트로 적은 좋아하는 것/싫어하는 것을 구조화된 태그로
정규화한다.

**입력/출력**: `POST /schedules` 요청 바디(dict) → `NormalizedConditions`.
`purpose`/`headcount`/`time_range`/`region`/`budget_per_person`은 프런트에서 이미
구조화해서 보낸 값이라 **LLM에 안 보내고 그대로 조립**한다 — 이미 맞는 데이터를
LLM이 다시 만들게 하면 틀릴 위험만 늘어난다는 판단. LLM은 `liked_text`/
`disliked_text`(자유 텍스트, 각 최대 100자)에서 `PreferenceTag` 태그만 추출하는 데
쓴다.

**프롬프트 설계 — RTF + few-shot**: 추출/분류 작업이라 CO-STAR 같은 콘텐츠 생성용
프레임워크보다 few-shot이 효과적이었다. few-shot 예시 4개는 각각 목적이 있다:
1. 기본 — 명시된 항목만 추출
2. 부정 표현 — "빼고/못 먹어요"의 대상이 disliked로 가야 함
3. 빈 입력 — 아무것도 지어내면 안 됨 (실제 관측된 할루시네이션 버그를 직접 겨냥)
4. 주관적 취향 — 분위기/혼잡도는 verifiable=false

추상적인 예시가 아니라 **DeepEval 골든셋에서 실제로 관측된 실패 사례를 그대로
예시로 박아넣는 게** 가장 효과적이었다(`normalize_step1.py`).

**모델 티어 — LOW → MID 격상**: 출력을 `list[str]`에서 `PreferenceTag`(태그명 +
`verifiable` 불리언, 필드 2개짜리 객체)로 스키마를 복잡화하자, LOW 티어
(`solar-mini`)가 `disliked_text`가 비었을 때 few-shot 예시 내용을 베끼거나
`liked` 항목을 `disliked`에 중복 삽입하는 문제가 DeepEval 골든셋으로 실측
확인됐다. MID(`solar-pro`)로 올리자 같은 골든셋 9/9 통과(0.80~1.00)로 즉시
해결(2026-08-07). 교훈: "간단해 보이는 작업"이라도 출력 스키마가 복잡해지면
티어를 재검증해야 한다.

**2026-08-12 후속 정리 — LOW 재정의**: 위 격상은 upstage(`solar-mini` 탈락)만
실측한 결과인데, `ModelTier`는 provider 공용이라 anthropic(`claude-haiku-4-5`)·
openai도 검증 없이 같이 MID로 올라간 상태였다. `pipeline/models.py`의 LOW를
"`solar-pro`/`gpt-5-mini`급 소형 모델"로 재정의(가격대를 provider 간 맞춤)하고
`solar-mini`는 LOW에서 뺐다 — Step1의 `TIER`는 아직 MID로 유지 중이며,
claude-haiku-4-5/gpt-5-mini로 위 골든셋을 다시 돌려 통과가 확인되면 LOW로
내리는 걸 다음 작업으로 남겨둔다(Solar만으로 내린 결론을 다른 provider에
그대로 적용하지 않는다는 원칙 유지).

**검증 불가능한 정보 처리 — `PreferenceTag.verifiable`**: "해산물"처럼 장소
카테고리로 나중에 확인 가능한 태그와 "사람 많은 곳"처럼 확인할 데이터 자체가
없는 태그를 섞어서 같은 강도로 다루면 안 된다는 문제의식. Step1은 이 둘을
`verifiable`로 명시적으로 태깅만 하고, 실제로 다르게 취급(하드 제약 vs 소프트
신호)하는 건 Step2의 몫이다.

**프롬프트 인젝션 고려**: 자유 텍스트가 그대로 프롬프트에 들어가므로 structured
output으로 출력 스키마를 강제하면 "다른 텍스트를 출력하게"는 만들 수 있어도
이후 파이프라인 흐름 자체를 바꾸지는 못한다는 점을 설계 시점에 확인해뒀다.

## Step2 — 후보 생성 (`generate_candidates`) — **구현 완료**

**목적**: MoA(Mixture of Agents)의 "Proposer" 단계. Step1이 만든
`NormalizedConditions` **한 세트**를 관점이 다른 프롬프트 3개로 병렬 호출해,
서로 실질적으로 다른 일정 초안(`CandidateDraft`) 3개를 만든다.

**왜 "다른 조건 3개"가 아니라 "1개 조건을 3가지 관점으로"인가**: 같은 조건을
반복 호출하면 겉보기만 다르고 구조적으로 비슷해지기 쉽다. 관점 자체를 프롬프트
레벨에서 다르게 박아 넣고 독립 호출해야 실질적으로 차별화된 결과가 나온다.
관점 3개(고정): (a) 실내 중심·가성비 우선 (b) 동선 최소화 우선 (c) 취향 태그
최대 반영.

**purpose(목적)별 프롬프트 가이던스(2026-08-11 추가)**: `purpose`(date/friends/
family/party/other)가 지금까지 유저 프롬프트에 `"목적: date"`처럼 원문 그대로만
들어가고 어떻게 반영하라는 구체 지시가 없었다 — budget/tags 등 다른 조건에는
전용 지시문이 있는데 purpose만 유일하게 LLM의 일반 상식에만 맡기는 구조였고,
실제로 잘 반영되는지 검증(eval 케이스 등)된 적도 없었다. `_PURPOSE_GUIDANCE`
딕셔너리로 목적별 구체 지시문(예: date → "2인이 나란히 즐기기 좋은 분위기 있는
장소 위주") 추가. `other`는 목적이 특정되지 않은 경우라 별도 지시 없이 무난하게
구성 — 그런데 프런트 `PURPOSES` 목록에 애초에 "기타" 옵션 자체가 빠져있던 걸
발견해(백엔드 `Literal`엔 이미 있었음) 같이 추가했다.

**"장소 선택"(LLM)과 "시간 배정"(결정론적 계산)을 분리 — 2026-08-09 결정**:
처음엔 LLM 호출 하나가 환각 방지·verifiable 하드/소프트·예산 합산·중복 방문
금지·시간 겹침 없음·관점 반영을 전부 동시에 지키게 시켰는데, MID는 물론 HIGH
티어로도 골든 5케이스 중 2~3개가 계속 실패했다(프롬프트를 여러 번 고쳐도
실패 패턴만 바뀌고 안 없어짐). 원인은 "겹치지 않는 시간 배정"이 사실 창의적
판단이 필요 없는 **결정론적 계산 문제**인데 이걸 LLM에게 다른 판단 작업들과
동시에 시켰다는 것 — LLM은 `CandidateSelectionDraft`(장소 이름·카테고리·
가격대·방문 순서만, 시작/종료 시각 없음)까지만 만들고, `_schedule_places()`가
그 순서대로 시간을 순차 배정한다(활동 하나당 30~90분, 활동 사이 이동 여유
30분 — 값은 실측 전 임의 설정). 순차 배정이라 활동끼리 겹치는 게 계산 구조상
아예 생기지 않는다 — "시간 겹침 없음"이 LLM이 지켜야 할 규칙에서 코드가
보장하는 성질로 바뀐 것. 분리 직후 같은 골든 5케이스가 5/5 통과(전부 0.80)로
바로 해결됨 — **LLM에게 한 번에 너무 많은 제약을 동시에 시키지 말고, 결정론적으로
계산 가능한 부분은 코드로 떼어내라**는 게 이 프로젝트에서 반복 확인된 처방
(Step1의 LOW→MID 격상도 비슷한 계열이지만, 이번엔 티어를 올리는 대신 아예
작업을 쪼갠 것이 다른 점).

**verifiable 처리 — Step1 태깅을 실제로 다르게 적용**:
- `verifiable=true`(해산물 등) → **하드 제약**. place_candidates의 카테고리/이름으로
  명확히 판단되면 확실히 반영/배제.
- `verifiable=false`(사람 많은 곳 등) → **소프트 신호**. 검증할 방법이 없으므로
  참고만 하고 보장하지 않는다고 프롬프트에 명시. `rationale`에도 "사람이
  없습니다"처럼 단정하지 않고 "비교적 한산한 편인 곳으로 골랐어요"처럼 hedge된
  표현을 쓰도록 지시 — 검증 못 한 걸 확신하는 것처럼 말하면 실제와 다를 때
  사용자 신뢰를 잃는다.

**미해결 설계 질문 (a)(b) — 해소됨(2026-08-11)**: 2026-08-10에 기록했던 "와플"
사례(태그가 여러 장소에 중복 반영되는 문제 (a), category/title 매칭만으로는
메뉴 존재를 보장 못 하는 정밀도 한계 (b)) 둘 다 다음과 같이 해결했다:

- **(a) 태그 중복 반영**: 관점 지시문(`_ROLE_TASK`)에 "같은 태그는 후보당 최대
  1곳이면 충분하다"를 추가(1차 방어) + `synthesize_step3._has_duplicate_tag_match()`가
  `ActivityDraft.matched_tag`(아래 참고) 기준으로 같은 태그가 2곳 이상이면
  하드 드롭(2차, 결정론적 강제) — 이 프로젝트가 반복 확인한 처방("LLM에게 한
  번에 너무 많이 시키지 말고, 결정론적으로 계산 가능한 부분은 코드로 떼어내라")
  을 그대로 적용.
- **(b) 매칭 정밀도**: 검토했던 두 방향(매칭 정밀도 강화 / 문구만 hedge) 중
  전자를 실제로 구현 — `naver_local_search.search_places_for_regions()`가
  이제 verifiable=true인 liked_tags/disliked_tags 태그마다 `"{region} {tag}"`
  (예: "강남 와플") 검색을 카테고리 검색과 별도로 추가 호출한다. category/title
  텍스트만 보고 LLM이 사후 추측하던 걸, "네이버 자체 검색 랭킹이 이 태그와
  연관 지은 장소"라는 더 강한 근거로 대체 — liked 매칭 결과는 place dict에
  `matched_tag`를 부착해 `ActivityDraft.matched_tag`까지 그대로 옮기고(Step2가
  참고, Step3의 (a) 하드룰 근거), disliked 매칭 결과는 결과 목록에서 아예
  제거해 Step2 LLM이 애초에 볼 수 없게 한다(기존 "category/title로 판단해
  배제해라" 프롬프트 지시는 2차 안전망으로 유지).
  - 실측으로 확인된 한계: "강남 와플" 태그 검색 결과에도 배스킨라빈스(아이스크림),
    초콜릿전문점처럼 무관한 곳이 섞여 나온다 — 태그 검색이 카테고리 검색보다
    정밀하지만 100% 보장은 아니다. 그래서 사용자에게 보여주는 문구(`why_recommended`)
    는 여전히 hedge 유지 — 매칭 근거를 강화하는 것과 확신에 찬 문구를 안 쓰는
    것 둘 다 같이 간다.
  - 호출량 제어: verifiable 태그 개수가 자유텍스트라 무제한이면 지역 확장(아래)과
    곱해져 호출량이 감당 안 된다 — `normalize_step1.py` 프롬프트가 좋아하는/
    싫어하는 것 각각 최대 3개까지만, 사용자가 더 중요하게 언급한 순서로 남기도록
    지시(1차)하고, `NormalizedConditions.cap_verifiable_tags` validator가 방어용
    하한선(2차, 초과해도 요청은 실패시키지 않고 조용히 자름 — LLM 품질 문제지
    사용자가 검증을 우회하려는 상황이 아니라서).

**세부지역 없는 광역 시/도 자동 확장(2026-08-11) — 아래 "지역 범위 축소"
(2026-08-11 2차)로 폐기됨**: "서울"처럼 세부지역 없이
시/도만 입력하면 지금까지 "서울 카테고리" 하나로 통짜 검색했는데, `app/services/
regions.py::expand_broad_region()`이 그 시/도의 세부지역들("서울 강남", "서울
홍대" 등, `moduyaksok-frontend/src/lib/regions.ts`의 REGIONS를 백엔드에 복제한
것)로 펼쳐서 각각 독립적으로 카테고리+태그 검색을 돈다. 카테고리당 10개로
늘리는 안도 검토했으나, 이 API의 `display` 파라미터가 `start`(페이지네이션)를
무시하는 걸 실측으로 확인해 포기 — 5개 고정 유지.

**이동거리 하드룰(2026-08-11)**: 위 지역 확장이나 사용자가 명시한 여러 지역
(예: 서울 강남 + 경기 수원)이 place_candidates 풀에 섞이면서, 하루 코스 안에
서로 먼 지역끼리 섞이는 문제가 생길 수 있다는 지적이 있었다. `synthesize_step3.
_has_excessive_travel()`이 `travel_estimate.estimate_buffer_minutes()`(이미
있는 좌표 기반 추정 함수 재사용)로 연속 활동 간 추정 이동시간을 계산해 임계값
(초기값 60분, `_MAX_TRAVEL_MINUTES`, 기존 시간 초과 관용 범위와 같은 감각의
초기 추정치 — 실측 후 조정 필요)을 넘으면 하드 드롭한다. 활동에 이미 결정론적
으로 붙어있는 좌표만 보고 판단하므로 "이 활동이 입력 지역 중 어디서 왔는지"를
따로 추적할 필요가 없다 — 명시적 다중 지역 케이스와 광역 확장 케이스를 하나의
메커니즘으로 같이 커버한다.

**네이버 지역검색 호출량 제어(2026-08-11)**: 태그 검색 + 광역 확장이 곱해지면서
한 `POST /schedules` 요청이 네이버 API HUB 한도(초당 10건, 일일 25,000건)를
순간적으로 넘길 수 있다는 게 계산상 명백해져 `app/services/rate_limiter.py`
신규 도입. `search_places()` 호출마다 세션(=요청 하나) 단위 라운드로빈 토큰버킷
(`_RoundRobinLimiter`)으로 초당 상한을 기다린다 — 처음엔 프로세스 전역 순수
FIFO 토큰버킷으로 시작했는데, "한 요청이 콜을 잔뜩 큐에 넣으면 다른 요청이
굶는다"는 지적을 받고 같은 날 업그레이드했다. 기존 토큰버킷(충전량·상한)에
"토큰이 생길 때마다 어느 세션 차례인지"만 라운드로빈으로 고르는 얇은 레이어를
씌운 구조라, 세션이 하나뿐이면 경쟁이 없어 기존 토큰버킷과 동일하게(버스트
포함) 동작하고 세션이 여럿일 때만 라운드로빈이 개입한다. `search_places_
for_regions()`가 쏘기 전에 Redis(`INCRBY`+자정 TTL) 기반 일일 예산을 먼저
확보한다. 예산이 부족하면 요청을 막지 않고 확보되는 만큼만 검색해
place_candidates가 적은 채로 진행한다(하드 실패보다 부분 결과가 낫다는 판단).

**관점 3개가 비슷한 후보를 만드는 문제(2026-08-11, 사용자 관측)**: "와플"을
포함해 실제로 일정을 만들어보니 3개 관점이 거의 같은 장소로 수렴하고, 심지어
한 후보 안이 베이커리 3곳으로만 채워지고 점심·저녁이 아예 없는 경우도 있었다.
원인은 `_ROLE_TASK`(관점 3개가 공유하는 공통 지시문)가 verifiable 태그 반영을
관점 구분 없이 지시하고 있었던 것 — "가성비"/"동선최소화" 관점도 강한 태그가
있으면 똑같이 그 태그를 만족하는 상위 장소를 욕심낼 이유가 있었고, 카테고리
구성(식사류 대 디저트류)에 대한 규칙이 아예 없어서 취향 반영이 과하면 카테고리가
한쪽으로 쏠려도 아무도 안 막았다. 두 가지로 해소:

- **관점별 태그 매칭 장소 분배(`generate_step2._tag_bundles_by_perspective()`)**:
  관점 3개에 완전히 동일한 place_candidates를 주던 것에서, verifiable 태그
  매칭 장소(`matched_tag`가 있는 것)만 관점마다 다른 부분집합으로 나눠주는
  것으로 변경(카테고리 검색으로만 나온 장소는 그대로 공유). 매칭이 제일 많은
  태그를 "시드 태그"로 삼아 관점마다 다른 시드 장소를 배정하고, 다른 태그는
  그 시드와 좌표(mapx/mapy — Step4 이동시간 추정과 같은 값, `travel_estimate.
  haversine_distance_m` 재사용)상 가장 가까운 매칭으로 채운다 — 관점 하나가
  보는 태그 매칭 장소들이 지리적으로 흩어지지 않으면서, 같은 곳을 여러 관점이
  아예 볼 수조차 없게 만든다. 처음엔 지역 문자열(예: "서울 강남")로 지역별
  검색 결과를 그룹핑하는 방향도 검토했으나(태그 검색이 이미 지역별로 나가서
  같은 지역 매칭끼리는 지리적으로 가깝다는 점 이용), 좌표(mapx/mapy)가 이미
  place_candidates에 있고 Step4가 실제로 쓰는 값과 같아서 새 필드 없이 바로
  쓰는 쪽이 더 간단하다고 판단해 좌표 기반으로 확정. 매칭이 관점 수보다 적으면
  자연히 겹칠 수 있음(정상 — 억지로 완전히 다르게 만들지 않는다).
  `generate_single_candidate()`(관점 재생성)도 같은 파티션을 인덱스로 다시
  계산해서 쓴다 — 안 그러면 재시도가 다른 관점 몫을 침범해서 다시 겹칠 수 있다.
- **식사 슬롯 하드룰**: `naver_local_search.py`가 카테고리 검색 버킷(맛집/카페/
  액티비티/문화시설) 중 어디서 나왔는지를 `source_category`로 place dict에
  부착(matched_tag와 완전히 같은 패턴 — 이유도 같다: 네이버 원본 category
  문자열은 카페도 "음식점>카페,디저트"로 묶여있어 실측 확인했듯 "식사 가능한
  곳"과 "디저트만 되는 곳"을 못 가르는데, 우리가 어떤 쿼리로 찾았는지는 확실한
  근거). `ActivityDraft.source_category`까지 그대로 옮긴 뒤:
  1. time_range가 점심(12:00~13:00)/저녁(18:00~19:00) 구간을 포함하면 그
     시간대에 `[맛집]` 표시된 카테고리 장소를 최소 1곳 포함하라고 유저
     프롬프트에 동적으로 지시한다(`generate_step2._meal_slot_instruction`,
     1차 방어) — 정확히 그 시각에 먹어야 한다는 뜻은 아니고, "그 시간대가
     일정에 껴 있으면 식사 하나는 넣는다"는 느슨한 기준(사용자 제안).
     `_format_place_candidates()`도 place 줄마다 `[맛집]` 같은 버킷 라벨을
     보여줘서 LLM이 텍스트로 카테고리를 추측하지 않고 바로 참조하게 한다.
  2. `synthesize_step3._has_missing_meal_slot()`이 그 시간대와 겹치는
     `source_category == "맛집"` 활동이 없으면 하드 드롭한다(2차, 결정론적
     강제) — "태그당 1곳"·"이동거리" 때와 같은 이유로 프롬프트 지시만 믿지
     않는다.

  나중에 피드백 단계(`POST /schedules/{id}/feedback`, 아직 미구현)에서
  "점심은 만나서 먹을 거예요" 같은 입력이 들어오면 이 식사 슬롯 요구사항
  자체를 덮어쓰게 확장하면 된다 — 지금 설계와 자연스럽게 이어짐.

**지역 범위 축소 + 카테고리 세분화 + 장소 풀 영속화(2026-08-11 2차)**: 사용자가
NAVER API HUB 공식 문서를 직접 확인해 `display`가 1~5로 제한되고 `start`
(페이지네이션)가 사실상 고정이라는 걸 재확인 — 여러 지역을 조합해서 받던
기존 구조는 지역을 쪼갤수록 지역당 결과만 희석되는 역효과가 있었다. 네 가지를
같이 바꿨다:

- **여러 지역 지원 포기, 세부지역 필수 단일 지역**: `NormalizedConditions.regions:
  list[str]` → `region: str`로 축소, `validate_region`이 세부지역 없는 값(예:
  "서울"만)을 거부한다. `app/services/regions.py`(광역 시/도 자동 확장)는
  이제 쓸 곳이 없어져 삭제 — 프런트 `moduyaksok-frontend/src/lib/regions.ts`의
  REGIONS/PROVINCES는 시/도+세부지역 선택 UI(`ConditionWizardView.vue`)에는
  계속 쓰여서 그대로 남는다.
- **카테고리 세분화**: `_PLACE_CATEGORIES`를 4개("맛집"/"카페"/"액티비티"/
  "문화시설")에서 15개(한식/중식/일식/양식/분식/고깃집/카페/베이커리/술집/
  액티비티/방탈출/보드게임카페/전시/공연장/영화관)로 세분화 — 카테고리 결과
  간 중복이 적어서(사용자 판단) 세분화해도 손해가 없고, `display` 상한(5)에
  걸려 있던 카테고리별 결과 수를 사실상 늘리는 효과가 있다. 식사 슬롯 하드룰이
  참조하던 `source_category == "맛집"`은 `_MEAL_CATEGORIES`(한식/중식/일식/양식/
  분식/고깃집) 집합 소속 여부로 대체(`naver_local_search.py`/`generate_step2.py`/
  `synthesize_step3.py` 세 파일에 독립적으로 유지 — 이 프로젝트의 기존 상수
  중복 관례).
- **MAX_VERIFIABLE_TAGS 3 → 5**: 지역 확장이 사라지면서 호출량 여유가 생겨
  좋아하는/싫어하는 것 각각 검색 가능한 verifiable 태그 상한을 5개로 올림
  (`normalize_step1.py`의 프롬프트 문구도 f-string으로 상수를 직접 참조하게
  바꿔서, 상한이 또 바뀌어도 프롬프트 텍스트를 깜빡하고 안 고치는 사고를 막음).
  카테고리(15개) × 태그(최대 10개) 쿼리 팬아웃으로 지역 하나당 최소 50개
  이상의 고유 장소를 모으는 게 목표.
- **`SchedulePlacePool` 테이블 신규(장소 풀 영속화)**: 지금은 매 `POST /schedules`
  요청마다 네이버 검색을 새로 하지만, 나중에 피드백(`POST /schedules/{id}/feedback`,
  아직 미구현)으로 일정을 수정할 때도 매번 새로 검색하면 낭비다. 검색된
  place_candidates와 이미 검색한 verifiable 태그 목록을 `schedule_session`과
  1:1(FK unique)로 연결된 별도 테이블에 저장해뒀다가, 피드백이 새 태그를
  요구할 때만 그 태그만 추가 검색하고 기존 풀에 누적시킬 수 있게 미리 준비한
  것 — 아직 피드백 엔드포인트 자체가 없어서 "쓰는" 쪽은 미구현, 이번엔 저장만
  구현. `schedule_place_pool`을 `schedule_session`의 컬럼으로 얹지 않고 별도
  테이블로 분리한 이유(정규화 논의): 두 데이터의 갱신 빈도와 읽히는 이유가
  다르다 — `schedule_session`(status/confirmed_candidate_id 등)은 확정 시점에만
  바뀌는 "핵심 엔티티"인 반면 `schedule_place_pool`은 피드백이 올 때마다 갱신될
  "생성용 내부 상태"라, 같은 row에 두면 조회 빈도가 훨씬 높은 `schedule_session`
  읽기(공유 화면, 목록 등)가 매번 필요 없는 큰 JSONB 블록을 같이 들고 다니게
  된다.

**환각 방지 — place_candidates**: 장소를 LLM이 아는 이름으로 그냥 던지지 않는다.
네이버 지역검색 API(`app/services/naver_local_search.py`, NAVER Developers 포털
발급, Step4가 쓸 네이버 지도 API와는 다른 상품·다른 키)로 사전 조회한 "지역 내
카테고리별 장소 후보 목록"을 프롬프트 컨텍스트로 주입하고, LLM은 그 목록 안에서만
장소를 선택하도록 지시한다. 이 조회는 `generate_candidates()` **함수 밖**(장래
`POST /schedules` 라우터)에서 끝내고 결과를 `place_candidates: list[dict]`로
넘긴다 — Step2를 "조건+장소 후보 → LLM 호출"만 하는 순수 함수로 유지해야 유닛
테스트에서 네트워크 mock 없이 `call_structured`만 mock하면 되기 때문.

**프롬프트 설계 — RTF만, few-shot 생략**: Step1과 달리 이건 정형 추출이 아니라
생성 작업이다. few-shot을 넣으면 3개 관점이 예시 스타일로 수렴해 "실질적
차별성 확보"라는 이 Step의 핵심 목표를 오히려 해칠 수 있다고 판단해 뺐다.

**모델 티어 — MID였다가 HIGH로 격상(2026-08-09)**: 후보마다 어느 정도 창의성이
필요하지만 3배로 병렬 호출되니 비용도 고려해 처음엔 MID로 정했으나, 예산
합산·중복 방문 금지 지시를 추가하자 MID가 여러 하드 제약을 동시에 못 버티는
게 실측 확인돼 HIGH로 올렸다. "장소 선택/시간 배정 분리" 이후에도 LLM이
여전히 예산·verifiable·관점 등 여러 판단을 하므로 HIGH 유지 중.

**부분 실패 정책**: 관점별 개별 timeout(~180초 — 각 호출이 실제로 얼마나
걸릴지 아직 실측 전이라 널널하게 잡음, 실측 후 필요하면 좁힘) + 개별 실패는
해당 관점만 스킵하고 나머지로 진행. 3개 다 실패해야 완전 실패로 취급
(`RuntimeError`).

**`rationale` 필드가 중요한 이유**: Step3가 후보 간 비교·랭킹 근거로 이 필드를
그대로 재사용한다 — Step2 시점부터 Step3를 염두에 두고 설계된 필드.

**활동 사이 버퍼 — 고정 30분에서 좌표 기반 추정으로 변경(2026-08-10)**: Step4가
경로를 "사용자가 후보를 고른 뒤"에만 조회하게 되면서(아래 Step4 절), Step2가 화면에
보여줄 시간을 배정하는 시점엔 실제 이동시간을 더더욱 알 수 없게 됐다. 그래서
place_candidates의 좌표(mapx/mapy)로 직선거리를 구하고, 도로 왜곡 보정(×1.3)과
도보/대중교통 평균 속도로 대략적 이동시간을 추정한 뒤 안전마진(×1.2)을 더해 버퍼로
쓴다(`app/pipeline/travel_estimate.py`의 `estimate_buffer_minutes()`). 좌표를 못
찾으면(place_candidates에 없는 환각 장소 등) 기존 고정 30분으로 폴백한다. 이 추정은
어차피 근사치이므로, Step4가 실제 이동시간을 알아내면 `reconcile_schedule()`로 그
구간 이후 활동들의 시간을 다시 맞춘다(아래 Step4 절 "Step2 추정과 실제값이 다를 때"
참고).

## Step3 — 검증·병합 (`synthesize_and_validate`) — **구현 완료(2026-08-10)**

**입력에 `conditions: NormalizedConditions` 추가(2026-08-10)**: 원래 스텁 시그니처엔
없었는데, 예산/시간 위반을 재검증하려면 `budget_per_person`/`time_range`가
필요해서 빠뜨릴 수 없었다.

**장소 환각 판단은 별도 조회 없이 `ActivityDraft.lat is None`으로 대신한다**:
Step2가 place_candidates에 없는 이름은 좌표를 못 붙이므로(`generate_step2.
_coords_by_title` 참고) 이미 있는 신호를 재사용 — place_candidates를 이 함수까지
새로 들고 올 필요가 없다.

**목적**: MoA의 "Aggregator" 단계. Step2에서 나온 3개 초안(장소·순서·시간은 이미
확정됨, 이동 경로는 아직 없음 — Step4가 사용자 선택 이후에 채운다)을 **한 번의
LLM 호출**에 모두 전달해 판단만 한다 — 구조를 재배치하지 않는다.

**왜 후보마다 따로 호출하지 않고 1번에 다 넣는가**: "후보끼리 비교"가 이 단계의
핵심 역할 중 하나라, 후보를 하나씩 따로 호출하면 다른 후보를 볼 방법이 없다.

**모델 티어 — HIGH**: 파이프라인에서 정확한 판단력이 품질을 가장 크게 좌우하는
단계(예산/시간 위반 재검증, 후보 드롭·재생성 판단, 최종 요약 작성)라 호출이
1회뿐임에도 가장 강한 모델을 쓴다.

**처리 순서**:
1. 예산/시간/조건 위반 재검증(규칙 기반 사전 필터링 + LLM 정성 판단 병행) —
   위반 종류마다 다른 강도로 다룬다(아래 "무엇이 엄격/관대인가" 참고)
2. 후보 간 유사도 검사(`_similarity_score`, 활동 이름 겹치는 비율을 자카드
   유사도로 LLM 호출 **전에** 미리 계산해서, 0.5 이상인 쌍이 있으면 그 정보를
   프롬프트 컨텍스트로 얹어 "겹치는 후보들의 why_recommended에는 서로 다른
   점을 강조해라"고 지시 — 유사도 자체가 드롭 사유는 아니다)
3. 하드 위반(장소 환각·활동 간 시간 겹침·time_range 대폭 초과·예산 대폭 초과)이
   있는 후보는 규칙 기반으로 LLM 호출 전에 드롭. verifiable=true 태그 위반은
   규칙만으로 못 잡아서(예: "해산물" 태그와 "이자카야" 카테고리가 겹치는지는
   의미 판단이 필요) 살아남은 후보를 LLM에 넣을 때 같이 재검증해 추가로 드롭될
   수 있다
4. 살아남은 후보 각각에 `why_recommended` 생성, `CandidateDraft`/`ActivityDraft`를
   최종 `Candidate`/`Activity`로 변환(order 부여, operating_hours는 항상 빈
   문자열+info_needs_check=True, `naver_map_url.build_naver_map_url()`로 만든
   `map_url` 추가 — 영업시간 자기확인 유도용 링크를 담을 필드가 기존 스키마엔
   없어서 Step3 구현하며 추가)

**재생성 최대 1회 — Step3가 아니라 별도 오케스트레이터가 담당(2026-08-10 확정,
`app/pipeline/orchestrate.py::generate_schedule_candidates`)**: 원래 설계는 하드
위반 후보를 그 관점으로 재생성까지 하는 거였는데, 이걸 Step3 안에서 하려면
place_candidates와 "이 후보가 어느 관점(가성비/동선최소화/취향반영)에서
나왔는지"를 Step3까지 새로 들고 와야 해서 Step2-Step3 결합이 커진다. 대신 이
프로젝트가 이미 따르던 관례("각 Step은 다른 Step을 안 부르고, 여러 Step을 잇는
건 오케스트레이터/라우터 몫" — Step1/2/4가 전부 이 패턴) 그대로 별도 함수로
뺐다. Step3 자체는 손대지 않고 순수하게 유지:

1. Step1→2→3을 순서대로 실행(`generate_candidates_with_perspectives()`로 각
   후보가 어느 관점에서 나왔는지 라벨 유지 — `generate_candidates()`는 라벨 없는
   기존 시그니처를 유지하는 얇은 래퍼로 바뀜, 하위호환)
2. Step3 결과에서 "어느 관점이 빠졌는지"는 스키마에 필드를 추가하지 않고
   `Candidate.title`을 원본 `CandidateDraft.title`과 문자열로 대조해서 알아낸다
   — Step3가 title을 그대로 복사하기 때문에(LLM이 새로 짓지 않음) 이 매칭으로
   충분하다. Step3 결과가 `InfeasibleResponse`(전부 드롭)면 시도했던 관점
   전부가 "빠진 관점"이다.
3. 빠진 관점마다 `generate_single_candidate()`(관점 1개만 동기 호출)로 재생성
   시도 — 실패하면(그 관점도 포기, 최대 1회이므로 더 재시도 안 함)
4. 재생성에 성공한 게 하나라도 있으면, 살아남은 기존 후보 + 재생성분을 합쳐
   Step3를 한 번 더 호출해 최종 결과로 삼는다

사용자에게는 이 재시도가 안 보인다 — `POST /schedules`(장래) 응답이 나가기 전에
`generate_schedule_candidates()` 안에서 다 끝난다(원래 설계 의도와 동일한 UX,
재시도가 일어나는 "위치"만 Step3 내부에서 오케스트레이터로 옮겼을 뿐).

**무엇이 엄격(hard)이고 무엇이 관대(soft)인가 — 2026-08-09 결정, 2026-08-09
수정**: 세 가지를 서로 다르게 다룬다.

- **활동 간 시간 겹침 — 항상 엄격**: 같은 candidate 안에서 두 활동이 동시간대에
  겹치는 건 정도의 문제가 아니라 구조적으로 불가능한 일정이다. 예외 없이
  하드 위반으로 드롭(Step2._schedule_places()가 순차 배정이라 구조적으로 이미
  안 생기지만, `_has_time_overlap()`으로 방어적으로 다시 확인한다).
- **time_range 경계 초과 — 관대, 관용 범위 60분(2026-08-10 확정)**: 전체 일정이
  사용자가 지정한 time_range를 약간 벗어나는 것(예: 예정보다 최대 1시간 늦게
  끝남)은 허용한다. 특히 Step4가 채워주는 실제 이동시간이 Step2가 잡아둔
  여유시간보다 더 걸려서 전체 일정이 밀리는 경우는 사용자·시스템 어느 쪽
  잘못도 아니라서, 예산과 같은 방식으로 처리한다 — 60분 이내면 드롭하지 않고
  `feasibility_warning`에 "예정보다 약 N분 더 걸릴 수 있어요" 같은 경고만
  채운다(`_time_overrun_minutes()`). 60분을 넘으면 하드 위반으로 드롭.
  이 값은 `travel_estimate.py`의 재조정 임계값(`_PULL_FORWARD_THRESHOLD_MINUTES`)
  과 같은 수치로 맞췄다 — 이 프로젝트의 "사소한 오차 허용선" 감각과 일치시킴.
  단, 이 단계가 보는 건 Step2의 **추정** 버퍼 기준이다 — 사용자가 후보를 고른 뒤
  Step4가 실제 이동시간을 채우고 나서 다시 초과가 확인되면, 그건 이 단계가 아니라
  Step4가 `feasibility_warning`을 갱신한다(아래 Step4 절 참고).
- **예산 초과 — 관대, 관용 범위 1인 예산의 20%(2026-08-10 확정)**: 식당 등의
  1인당 가격 자체가 `price_range_per_person`처럼 애초에 추정 범위이기 때문에,
  근소한 초과까지 하드 위반으로 잡으면 오히려 과민 반응이 된다.
  - 예산 초과가 **20% 이내**(`_budget_overrun_ratio()`)면 후보를 드롭하지 않고
    그대로 살려두되, `Candidate.feasibility_warning`에 "1인 예산보다 약 N원 더
    필요해요" 같은 문구를 채운다 — 새 필드를 추가하지 않고 기존 필드를
    재사용한다. 사용자가 이 경고를 보고 진행할지 조건을 다시 조정할지는
    프런트 몫.
  - 20%를 **넘으면** 하드 위반으로 취급해 드롭.

time_range 초과와 예산 초과 둘 다 관용 범위 안이면 같은 `feasibility_warning`
필드에 이유를 이어붙이면 된다(예: "예정보다 약 20분 더 걸리고, 예산도 약
3,000원 더 필요해요") — 필드 하나로 여러 경고를 다 표현할 수 있다.

**후보 개수는 3개를 억지로 보장하지 않는다 — 2026-08-09 결정**: 일부 후보가
규칙 기반 필터나 LLM 판단으로 드롭되면, 남은 개수(2개, 1개)를 그대로 사용자에게
보여준다. 3개를 채우겠다고 무리해서 조건에 안 맞는 후보를 욱여넣지 않는다.
유효한 후보가 **0개**가 된 경우에만 `InfeasibleResponse`로 빠진다 — 규칙 기반
필터링만으로 이미 0개면 LLM 호출 자체를 생략한다(비용 절약).

**랭킹 없음**: 후보는 서로 다른 관점(가성비/동선최소화/취향반영)으로 만들어진
것이라 "AI가 뽑은 1등"이 아니라 동등한 선택지로 제시한다(개수가 3개가 아니어도
동일). `candidate_id`도 순위를 암시하는 숫자(1/2/3) 대신 문자(A/B/C, 개수만큼만
부여)를 쓴다. `why_recommended`는 "왜 1등인지"가 아니라 "이 후보의 강점이 뭔지"를
설명하는 문장.

**`InfeasibleResponse`**: 유효한 후보가 0개일 때만 반환한다(Step2가 관점 3개
모두 실패한 경우도 결국 여기로 흡수됨). 프런트는 "생성 가능한 일정이 없어요 ㅠㅠ
조건을 다시 설정해주세요" 같은 안내와 함께 조건 입력 화면으로 돌아가는 버튼을
보여준다(2026-08-09 결정) — `adjustable_conditions` 필드는 나중에 "이 조건들을
특히 조정해보세요"처럼 힌트를 더 주고 싶을 때 쓸 수 있게 남겨두되, 지금 단계의
필수 요구사항은 아니다.

## Step4 — 이동 동선 보강 (`enrich_routes`) — **구현 완료(2026-08-10)**

**목적**: Step2가 만든 각 후보의 장소 시퀀스(순서·시간 이미 확정)는 재배치하지
않고, 구간 사이사이에 이동 정보만 채워 넣는다. LLM을 쓰지 않고 길찾기 API만
호출한다(판단이 필요 없는 단순 조회 단계라 모델 티어 해당 없음).

**3개 후보 전부가 아니라, 사용자가 고른 1개에만 실행(2026-08-10 파이프라인 순서
재설계, "전체 흐름" 절 참고)**: Step3까지 끝나면 경로 없는 후보 3개를 사용자에게
보여주고, 사용자가 그중 하나를 선택한 뒤에만 이 함수를 호출한다. 나머지 2개
후보에는 애초에 ODsay를 안 부르므로 Basic 등급(일 1,000건)을 아낀다.

**길찾기 프로바이더 — 네이버 → 카카오모빌리티 → ODsay로 변경(2026-08-09 결정,
2차 정정)**: 원래 네이버 지도 Directions API를 쓸 계획이었으나, NCP가 지도 API
신규 이용 신청을 차단하고 무료 이용량 제공도 중단했다(2025-03-24 공지 확인,
신규 발급 사실상 불가). 1차 대안으로 카카오모빌리티를 검토했으나, 실제 제품
페이지(`developers.kakaomobility.com`)를 직접 확인한 결과 **카카오모빌리티
길찾기 API는 자동차/다중경유지/다중출발지·목적지 전용이고 대중교통·도보
길찾기를 셀프서비스로 제공하지 않는다는 사실을 뒤늦게 확인**해 정정한다
(이전 버전 문서의 "카카오모빌리티가 대중교통 길찾기를 셀프서비스로 제공"이라는
서술은 저품질 검색 요약을 근거로 한 오판이었음). 재조사 결과:
- 구글 지도 API: 월 $200 무료 크레딧이 2025-03 폐지되고 SKU별 월 무료 한도로
  대체됨(Essentials 등급 기준 SKU당 월 10,000건). 결제 계정(카드) 등록 필수.
- **ODsay**(lab.odsay.com): 국내 대중교통 길찾기 전문 API. 개인/학생/5인 이하
  스타트업 대상 무료 "Basic" 등급으로 일 1,000건 호출 가능. 대중교통(지하철+버스
  조합) 경로에 도보 구간·소요시간·요금·환승 횟수·정류장 좌표를 포함해서 준다.
  기본 응답은 정류장 단위 좌표만 주지만, 응답의 `mapObj` 값으로 별도 그래픽
  데이터 API(`loadLane`)를 호출하면 경로를 따라 촘촘히 찍힌 "보간점" 좌표를
  받아 프런트 지도에 실제 확정 경로 그대로 선을 그릴 수 있다(공식 API
  레퍼런스 기준 확인, 실제 응답 샘플은 이 단계 구현 시 키 발급 후 실측 예정).
  출발-도착이 700m 이내로 가까우면 대중교통 검색 자체가 에러(`-98`,
  "출, 도착지가 700m이내입니다")를 반환하므로 이 경우는 백엔드에서 직선거리
  기반 도보로 폴백 처리한다. 참고로 ODsay가 계산하는 도보 구간(환승 이동 등)도
  직선거리 기반 근사치이며, 실제 보행자 경로 엔진은 ODsay의 유료 Map Browser
  쪽에서만 제공한다.
- 국토교통부(TAGO) 공개 API: data.go.kr에 공개된 것들은 버스 실시간 위치·
  도착정보 같은 개별 데이터 조회이고, 좌표 기반 경로 탐색(길찾기) 기능이 없어
  대안이 될 수 없음. 서울시 대중교통환승경로 조회 서비스는 서울 한정이라
  다중 지역을 지원하는 이 프로젝트엔 부적합.

→ **ODsay로 결정**. Step2가 쓰는 네이버 지역검색은 그대로 유지 — 장소 검색
(Step2)과 길찾기(Step4) 프로바이더가 달라져도, 길찾기는 장소 이름이 아니라
**좌표(위도/경도)만 있으면 되는 순수 기하학 문제**라 프로바이더가 그 장소를
"알고 있는지"와 무관하게 동작한다. 다만 네이버 지역검색이 주는 `mapx`/`mapy`는
네이버 자체 좌표계라, ODsay API에 넘기기 전에 표준 좌표계(WGS84)로 변환하는
과정이 필요하다 — 이 단계 구현 시 처리할 것.

**영업시간(`Activity.operating_hours`/`info_needs_check`) — 자동 확인 포기,
링크로 사용자 자기확인 유도(2026-08-09 결정)**: 네이버 지역검색·카카오 로컬
API 둘 다 장소 검색 결과에 영업시간 필드를 안 준다(실측 확인 — 구글 Places는
있지만 국내 소상공인 커버리지가 불확실해서 채택 안 함). 그래서 시스템이
영업시간을 자동으로 검증하는 건 포기하고, `info_needs_check=True`로 항상
표시하면서 `app/services/naver_map_url.py`의 `build_naver_map_url()`로 만든
그 장소의 네이버 지도 링크를 같이 보여줘서 사용자가 클릭 한 번으로 직접
확인할 수 있게 한다 — "검증 못 한 걸 확신하는 것처럼 말하지 않는다"는 이
프로젝트의 기존 원칙과 같은 결.

**교통수단 옵션을 자동으로 하나만 고르지 않는 이유**: 구간마다 옵션(도보/대중
교통, 차량은 아래 참고)을 전부 담아 `RouteSegment.options`로 반환하고, 사용자가
프런트에서 직접 고르게 한다. 사용자가 원치 않는 교통편이 자동으로 확정되면
UX가 깨진다는 판단(2026-08-07 논의). `recommended_mode`는 프런트 기본 선택값
(예: 최단 소요시간)일 뿐 최종 결정이 아니다.

**차량(자동차) 옵션 — NCP Maps Directions 5로 구현 완료(2026-08-10)**: `RouteOption.mode`의
`car`는 원래 카카오모빌리티를 붙일 계획으로 보류해뒀었는데, 콘솔에서 NCP
Maps(Directions 5)의 신규 이용 신청이 실제로 열려 있는 걸 확인해 그쪽으로 구현을
마쳤다 — `services/naver_directions.py::get_car_option()`, `enrich_step4.py`에
도보·대중교통과 나란히 연결됨(`moduyaksok-backend/schedule.md` 참고). 처음엔
errorCode 210 "구독 필요"가 떴는데, 콘솔의 "Maps"(VPC) Application은 레거시
`naveropenapi.apigw.ntruss.com`이 아니라 `maps.apigw.ntruss.com`을 써야 한다는
걸 확인해 도메인을 수정해 해결했다. 카카오모빌리티는 더 이상 필요 없어 보류
목록에서 제외.

**도보 정밀 경로(실제 인도를 따라가는 선) — 보류(TMAP 보행자 경로 API),
2026-08-10 결정**: 지금 도보 구간(`get_walk_option()`)은 API 호출 없이 직선거리
기반 근사치를 쓴다 — ODsay 대중교통 경로 안의 도보 구간(환승 이동 등)도 마찬가지로
직선 근사이고, 실제 보행자 경로 엔진은 ODsay의 유료 Map Browser 쪽에서만 준다(위
프로바이더 재조사 절 참고). 프런트에 Dynamic Map을 붙여 경로를 실제로 그리게 되면
도보 구간만 직선으로 튀어 보이는 문제가 생길 수 있다. 조사해보니 TMAP(SK텔레콤,
`apis.openapi.sk.com/tmap/routes/pedestrian`)이 국내에서 셀프서비스로 도보 전용
길찾기를 제공하는 사실상 유일한 API다(2026-08-10 조사). 다만 이걸 붙이면
프로바이더가 하나 더 늘어난다(ODsay=대중교통, NCP Maps Directions=자차,
TMAP=도보) — 별도 가입(openapi.sk.com)·별도 키·별도 연동 코드가 필요해서 지금은
붙이지 않는다. 실제로 지도에 그려봤을 때 도보 구간의 직선이 얼마나 거슬리는지
체감한 뒤에 필요성을 다시 판단할 것.

**막차/첫차 확인 — 자동 검증 포기, 영업시간과 같은 자기확인 유도 패턴(2026-08-10
정정)**: 원래 "구간별 실제 출발 시각을 ODsay에 넘겨서 막차 끊김을 감지한다"고
설계했었는데, 실제로 `searchPubTransPathT`를 실측해보니 이 API는 출발 시각을 받는
파라미터 자체가 없다(좌표만 받는 정적 그래프 탐색 — API 레퍼런스 확인,
2026-08-10). 즉 이 프로바이더로는 "이 시간에 막차가 있는지"를 확인할 방법이 없다.
그래서 시스템이 막차/첫차 여부를 자동으로 검증하는 건 포기하고, `operating_hours`/
`info_needs_check`와 같은 패턴으로 — "이동 시간대가 늦거나 이르면 막차/첫차 여부를
직접 확인하라"는 안내를 사용자에게 보여주는 쪽으로 처리한다. `RouteSegment.options`는
그 구간의 최적 경로 하나만 반환하고(시간 무관), 요일·시간대에 따라 실제로는 안 다닐
수 있다는 hedge를 프런트가 같이 보여준다.

**Step2 추정과 실제값이 다를 때 — 이후 활동 시간 재조정(2026-08-10 결정, 기존
"미해결 설계 질문" 해소)**: Step2는 좌표 기반 직선거리 추정으로 버퍼를 배정했을
뿐이라(위 Step2 절 참고) 실제 이동시간과 다를 수 있다. `enrich_routes()`는 구간마다
`recommended_mode`의 실제 소요시간과 Step2 추정 버퍼를 비교해
`travel_estimate.reconcile_schedule()`로 그 구간 이후 활동들의 `start_time`/
`end_time`을 조정한다:
- 실제가 추정보다 길면(초과): 반드시 뒤로 민다 — 안 그러면 활동끼리 시간이 겹친다.
- 실제가 추정보다 60분 넘게 짧으면(여유 과다): 앞으로 당겨서 불필요한 공백을 줄인다.
- 그 사이(60분 이내 차이)는 건드리지 않는다 — 사소한 차이로 매번 흔들리지 않게.

사용자가 `recommended_mode`가 아닌 다른 옵션을 고르는 경우(예: 도보 15분 대신 택시
5분)도 같은 `reconcile_schedule()`을 그 시점에 다시 호출하면 된다 — 이 함수 자체는
"추천값 기준 1회 조정"만 하므로, 사용자가 나중에 옵션을 바꿀 때 재호출하는 부분은
프런트 연동 시(그 옵션 변경을 받는 엔드포인트 설계 시) 구현한다.

**ODsay 키 발급·실측 완료(2026-08-10)**: `lab.odsay.com`에 학생 등급으로 애플리케이션
등록, 서비스 플랫폼은 URI 방식(로컬 `localhost:8000` / Render 배포본
`moduyaksok.onrender.com`)으로 등록해 `ODSAY_API_KEY`/`ODSAY_REFERER_URL`을
`.env`에 채웠다(서버 IP 방식은 Render가 고정 단일 IP를 안 줘서 폐기 — 아웃바운드
IP 대역만 제공하는데 ODsay 폼이 CIDR을 안 받음). 호출부는 `Referer` 헤더를
`ODSAY_REFERER_URL` 값으로 직접 세팅해야 통과된다(브라우저가 아니라 백엔드가
서버 대 서버로 호출하는 구조라 자동으로 안 붙음).

**mapx/mapy 좌표계 실측 결과 — 변환 불필요**: "네이버 지역검색 mapx/mapy가
자체 좌표계라 WGS84 변환이 필요하다"고 적었던 위 문단은 레거시 API(구
openapi.naver.com) 기준 추측이었다. 실제로 NAVER API HUB로 이관된 지금
엔드포인트(`naver_local_search.py`)를 실측해보니 mapx/mapy는 **WGS84 경도/위도
값에 10^7을 곱한 정수**였다(강남역·서울시청 인근 검색 결과를 실제 좌표와 대조해
확인, 2026-08-10). 좌표계 변환 로직 없이 `int(mapx) / 1e7`, `int(mapy) / 1e7`로
바로 쓰면 된다.

**700m 이내 폴백 실측 확인**: 700m 이내 좌표쌍으로 호출하면 `{"error": {"code":
"-98", "msg": "출, 도착지가 700m이내입니다."}}`가 그대로 재현됨 — 설계했던 대로
이 에러를 감지해서 직선거리 기반 도보로 폴백 처리하면 된다.

## 공통 인프라

- **`app/services/structured_llm.py`의 `call_structured()`**: Step1/2/3이 이
  함수 하나로 provider(Claude=tool use, GPT/Upstage=`.parse()` 공용)별 구조화
  출력을 통일해서 받는다(LLM을 쓰는 세 단계 — Step4는 LLM을 안 씀). Solar가
  openai SDK 호환이라고 최신 기능까지 지원할 거라 가정하지 않고 실측해서
  GPT/Solar를 1갈래로 합침(2026-08-07).
- **`app/pipeline/models.py`의 `get_model(provider, tier)`**: 모델 티어
  (LOW/MID/HIGH)를 provider별 실제 모델 ID로 매핑하는 곳을 한 곳으로 모음.
  작업 성격(단순 추출 vs 창의성 필요 vs 비교·판단)으로 먼저 정하고, 출력
  스키마가 바뀌면 재검증한다는 원칙(Step1에서 확인됨).
- **DB 저장**: `schedule_session.conditions`/`candidates`는 JSONB 컬럼 —
  파이프라인 스키마가 자주 바뀌는 시기라 마이그레이션 없이 대응하기 위함.
  Step2 산출물(검증 전 초안)을 위한 별도 컬럼은 없음 — Step3 결과부터
  `candidates` 컬럼에 쓴다(위 "전체 흐름"의 DB 저장 지점 논의 참고).
- **async 파이프라인 함수 + DeepEval eval 테스트를 같이 쓸 때 주의할 점**
  (Step2 구현 중 실측으로 확인, Step3/4도 동일하게 적용될 것): `asyncio.wait_for`
  /`asyncio.timeout`은 DeepEval의 `GEval.measure()`가 내부적으로 거는
  `nest_asyncio` 패치와 상충한다 — 한 pytest 세션 안에서 `async def` 테스트
  함수가 이미 실행 중인 이벤트루프 위에서 `metric.measure()`를 부르면(내부적으로
  또 `loop.run_until_complete()`를 재진입), "RuntimeError: Timeout should be
  used inside a task"로 실패한다. 대응 2가지: (1) eval 테스트 함수는 Step1처럼
  **동기 `def`**로 두고 그 안에서 `asyncio.run(...)`으로 파이프라인 함수를
  호출할 것(테스트마다 새 이벤트루프가 생성·종료돼 재진입 문제가 안 생김).
  (2) 파이프라인 함수 자체도 `asyncio.wait_for`/`asyncio.timeout` 대신
  `concurrent.futures.Future.result(timeout=...)`로 타임아웃을 걸 것 — 어떤
  이벤트루프 상태에서 호출되든 영향받지 않아 더 안전하다(`generate_step2.py`의
  `_call_all_perspectives_sync` 참고).
