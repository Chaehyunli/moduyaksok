# AI 파이프라인 Step별 상세 설계

`docs/기술설계_2026-08-06.md` §4(거시 설계)와 `moduyaksok-backend/CLAUDE.md`(결정 배경), 각
`app/pipeline/*_step*.py`의 docstring(구현 세부)에 흩어져 있던 "이 Step을 왜 이렇게
설계했는지"를 Step별로 모아 정리한 문서. 스키마 자체(필드명, 타입)는
`app/pipeline/schemas.py`가 원본이니 여기서는 "왜"에 집중한다.

## 전체 흐름

Step1 → Step2 → Step3 → Step4 **순차 실행**. 오케스트레이션 프레임워크(LangGraph 등)
없이 plain async 함수 체인으로 구성한다. 병렬화 지점은 **Step2 내부의 관점 3개
fan-out 하나뿐** — 나머지 Step 간에는 병렬화가 없다. DB(`schedule_session`)에는
Step4 최종 결과(`candidates` JSONB)만 저장되고, Step1~3의 중간 산출물은 요청 하나의
생명주기 동안 메모리에서만 존재한다(스키마가 자주 바뀌는 시기라 마이그레이션 없이
대응하기 위한 선택, `기술설계_2026-08-06.md` §6).

파이프라인 오류/타임아웃 공통 정책(§4): 각 LLM 호출에 개별 timeout을 걸고, 개별
실패는 스킵하고 나머지로 진행 — 완전 실패는 관련된 호출이 전부 실패했을 때만.
프런트 로딩 UX는 MVP 기준 스트리밍(SSE) 없이 단순 로딩 스피너 + 동기 응답(§4, §7).

## Step1 — 조건 정규화 (`normalize_conditions`) — **구현 완료**

**목적**: 사용자가 자유 텍스트로 적은 좋아하는 것/싫어하는 것을 구조화된 태그로
정규화한다.

**입력/출력**: `POST /schedules` 요청 바디(dict) → `NormalizedConditions`.
`purpose`/`headcount`/`time_range`/`region`/`budget_per_person`은 프런트에서 이미
구조화해서 보낸 값이라 **LLM에 안 보내고 그대로 조립**한다 — 이미 맞는 데이터를
LLM이 다시 만들게 하면 틀릴 위험만 늘어난다는 판단. LLM은 `liked_text`/
`disliked_text`(자유 텍스트, 각 최대 100자)에서 `PreferenceTag` 태그만 추출하는 데
쓴다.

**프롬프트 설계 — RTF + few-shot**: 추출/분류 작업이라 CO-STAR 같은 콘텐츠 생성용
프레임워크보다 few-shot이 효과적이었다. few-shot 예시 4개는 각각 목적이 있다:
1. 기본 — 명시된 항목만 추출
2. 부정 표현 — "빼고/못 먹어요"의 대상이 disliked로 가야 함
3. 빈 입력 — 아무것도 지어내면 안 됨 (실제 관측된 할루시네이션 버그를 직접 겨냥)
4. 주관적 취향 — 분위기/혼잡도는 verifiable=false

추상적인 예시가 아니라 **DeepEval 골든셋에서 실제로 관측된 실패 사례를 그대로
예시로 박아넣는 게** 가장 효과적이었다(`normalize_step1.py`).

**모델 티어 — LOW → MID 격상**: 출력을 `list[str]`에서 `PreferenceTag`(태그명 +
`verifiable` 불리언, 필드 2개짜리 객체)로 스키마를 복잡화하자, LOW 티어
(`solar-mini`)가 `disliked_text`가 비었을 때 few-shot 예시 내용을 베끼거나
`liked` 항목을 `disliked`에 중복 삽입하는 문제가 DeepEval 골든셋으로 실측
확인됐다. MID(`solar-pro`)로 올리자 같은 골든셋 9/9 통과(0.80~1.00)로 즉시
해결(2026-08-07). 교훈: "간단해 보이는 작업"이라도 출력 스키마가 복잡해지면
티어를 재검증해야 한다.

**검증 불가능한 정보 처리 — `PreferenceTag.verifiable`**: "해산물"처럼 장소
카테고리로 나중에 확인 가능한 태그와 "사람 많은 곳"처럼 확인할 데이터 자체가
없는 태그를 섞어서 같은 강도로 다루면 안 된다는 문제의식. Step1은 이 둘을
`verifiable`로 명시적으로 태깅만 하고, 실제로 다르게 취급(하드 제약 vs 소프트
신호)하는 건 Step2의 몫이다.

**프롬프트 인젝션 고려**: 자유 텍스트가 그대로 프롬프트에 들어가므로 structured
output으로 출력 스키마를 강제하면 "다른 텍스트를 출력하게"는 만들 수 있어도
이후 파이프라인 흐름 자체를 바꾸지는 못한다는 점을 설계 시점에 확인해뒀다.

## Step2 — 후보 생성 (`generate_candidates`) — **구현 완료**

**목적**: MoA(Mixture of Agents)의 "Proposer" 단계. Step1이 만든
`NormalizedConditions` **한 세트**를 관점이 다른 프롬프트 3개로 병렬 호출해,
서로 실질적으로 다른 일정 초안(`CandidateDraft`) 3개를 만든다.

**왜 "다른 조건 3개"가 아니라 "1개 조건을 3가지 관점으로"인가**: 같은 조건을
반복 호출하면 겉보기만 다르고 구조적으로 비슷해지기 쉽다. 관점 자체를 프롬프트
레벨에서 다르게 박아 넣고 독립 호출해야 실질적으로 차별화된 결과가 나온다.
관점 3개(고정): (a) 실내 중심·가성비 우선 (b) 동선 최소화 우선 (c) 취향 태그
최대 반영.

**verifiable 처리 — Step1 태깅을 실제로 다르게 적용**:
- `verifiable=true`(해산물 등) → **하드 제약**. place_candidates의 카테고리/이름으로
  명확히 판단되면 확실히 반영/배제.
- `verifiable=false`(사람 많은 곳 등) → **소프트 신호**. 검증할 방법이 없으므로
  참고만 하고 보장하지 않는다고 프롬프트에 명시. `rationale`에도 "사람이
  없습니다"처럼 단정하지 않고 "비교적 한산한 편인 곳으로 골랐어요"처럼 hedge된
  표현을 쓰도록 지시 — 검증 못 한 걸 확신하는 것처럼 말하면 실제와 다를 때
  사용자 신뢰를 잃는다.

**환각 방지 — place_candidates**: 장소를 LLM이 아는 이름으로 그냥 던지지 않는다.
네이버 지역검색 API(`app/services/naver_local_search.py`, NAVER Developers 포털
발급, Step3가 쓸 네이버 지도 API와는 다른 상품·다른 키)로 사전 조회한 "지역 내
카테고리별 장소 후보 목록"을 프롬프트 컨텍스트로 주입하고, LLM은 그 목록 안에서만
장소를 선택하도록 지시한다. 이 조회는 `generate_candidates()` **함수 밖**(장래
`POST /schedules` 라우터)에서 끝내고 결과를 `place_candidates: list[dict]`로
넘긴다 — Step2를 "조건+장소 후보 → LLM 호출"만 하는 순수 함수로 유지해야 유닛
테스트에서 네트워크 mock 없이 `call_structured`만 mock하면 되기 때문.

**프롬프트 설계 — RTF만, few-shot 생략**: Step1과 달리 이건 정형 추출이 아니라
생성 작업이다. few-shot을 넣으면 3개 관점이 예시 스타일로 수렴해 "실질적
차별성 확보"라는 이 Step의 핵심 목표를 오히려 해칠 수 있다고 판단해 뺐다.

**모델 티어 — MID**: 후보마다 어느 정도 창의성이 필요하지만 3배로 병렬 호출되니
비용도 고려해 MID로 정함(HIGH는 Step4에서 1회만 쓰는 것으로 아낌).

**부분 실패 정책**: 관점별 개별 timeout(~180초 — 각 호출이 실제로 얼마나
걸릴지 아직 실측 전이라 널널하게 잡음, 실측 후 필요하면 좁힘) + 개별 실패는
해당 관점만 스킵하고 나머지로 진행. 3개 다 실패해야 완전 실패로 취급
(`RuntimeError`).

**`rationale` 필드가 중요한 이유**: Step4가 후보 간 비교·랭킹 근거로 이 필드를
그대로 재사용한다 — Step2 시점부터 Step4를 염두에 두고 설계된 필드.

## Step3 — 이동 동선 보강 (`enrich_routes`) — **설계 확정, 미구현**

**목적**: Step2가 만든 각 후보의 장소 시퀀스(순서·시간 이미 확정)는 재배치하지
않고, 구간 사이사이에 이동 정보만 채워 넣는다. LLM을 쓰지 않고 네이버 지도
Directions API만 호출한다(판단이 필요 없는 단순 조회 단계라 모델 티어 해당
없음).

**교통수단 옵션을 자동으로 하나만 고르지 않는 이유**: 구간마다 옵션(도보/대중
교통/차량)을 전부 담아 `RouteSegment.options`로 반환하고, 사용자가 프런트에서
직접 고르게 한다. 사용자가 원치 않는 교통편이 자동으로 확정되면 UX가 깨진다는
판단(2026-08-07 논의). `recommended_mode`는 프런트 기본 선택값(예: 최단
소요시간)일 뿐 최종 결정이 아니다.

**조회 시각 — "지금 시각" 대신 구간별 실제 출발 시각**: 각 구간의 조회 시각은
그 구간 직전 활동의 `end_time`을 출발 시각으로 넣어야 한다. "지금 시각" 기준으로
조회하면 늦은 시간대 일정에서 막차가 끊긴 걸 놓치고 엉뚱한 경로를 보여주게 되는
문제가 있다. 특정 시간대에 옵션이 아예 없으면(막차 없음 등) `options`가 비거나
줄어들 수 있고, 그 경우 `feasibility_warning`에 사유를 채운다. 전체 이동시간
합산이 `time_range`를 넘기는 경우도 `feasibility_warning`에 채워 Step4에서
감점 요인으로 쓴다.

**미해결 설계 질문**: 사용자가 `recommended_mode`가 아닌 다른 옵션을 고르면
(예: 도보 15분 대신 택시 5분) 이후 활동들의 `start_time`/`end_time`을 자동으로
당길지 그대로 둘지는 아직 안 정함 — 프런트 UI 붙일 때 같이 결정하기로 함.

**블로커**: 네이버 지도 API 키(`NAVER_MAP_CLIENT_ID/SECRET`, NCP 콘솔 발급)
필요 — Step2의 `NAVER_SEARCH_CLIENT_ID/SECRET`과는 다른 키.

## Step4 — 검증·병합 (`synthesize_and_validate`) — **설계 확정, 미구현**

**목적**: MoA의 "Aggregator" 단계. Step2~3에서 나온 3개 초안(장소·순서·시간·
이동경로는 이미 확정됨)을 **한 번의 LLM 호출**에 모두 전달해 판단만 한다 —
구조를 재배치하지 않는다.

**왜 후보마다 따로 호출하지 않고 1번에 다 넣는가**: "후보끼리 비교"가 이 단계의
핵심 역할 중 하나라, 후보를 하나씩 따로 호출하면 다른 후보를 볼 방법이 없다.

**모델 티어 — HIGH**: 파이프라인에서 정확한 판단력이 품질을 가장 크게 좌우하는
단계(예산/시간 위반 재검증, 후보 드롭·재생성 판단, 최종 요약 작성)라 호출이
1회뿐임에도 가장 강한 모델을 쓴다.

**처리 순서**:
1. 예산/시간/조건 위반 재검증(규칙 기반 사전 필터링 + LLM 정성 판단 병행)
2. 후보 간 유사도 검사(`_similarity_score`, 활동 이름 겹치는 비율을 자카드
   유사도로 LLM 호출 **전에** 미리 계산해서 겹침이 심한 쌍이 있으면 그 정보를
   프롬프트 컨텍스트로 얹어 "겹치는 후보는 대체안으로 바꿔라"고 지시)
3. 위반(예산/시간/유사도 포함)이 심한 후보는 드롭, 필요하면 해당 관점으로
   재생성 **최대 1회** 요청(무한루프 방지 — 새 재시도 경로를 따로 만들지 않고
   이 함수의 기존 재시도에 태움)
4. 살아남은 (최대) 3개 각각에 `why_recommended` 생성

**랭킹 없음**: 3개는 서로 다른 관점(가성비/동선최소화/취향반영)으로 만들어진
것이라 "AI가 뽑은 1등"이 아니라 동등한 선택지 3개로 제시한다. `candidate_id`도
순위를 암시하는 숫자(1/2/3) 대신 문자(A/B/C)를 쓴다. `why_recommended`는
"왜 1등인지"가 아니라 "이 후보의 강점이 뭔지"를 설명하는 문장.

**`InfeasibleResponse`**: 후보가 하나도 유효하지 않으면(장소 자체가 없거나
예산으로 불가능) 사유 + 완화 가능한 조건 제안을 담아 반환한다. Step2가 관점
3개 모두 실패해 후보를 하나도 못 만든 경우도 Step4로 넘길 후보가 0개가 되므로
결국 이 규칙에 흡수되어 409 `InfeasibleResponse`로 나가는 구조다.

## 공통 인프라

- **`app/services/structured_llm.py`의 `call_structured()`**: Step1/2/4가 이
  함수 하나로 provider(Claude=tool use, GPT/Upstage=`.parse()` 공용)별 구조화
  출력을 통일해서 받는다. Solar가 openai SDK 호환이라고 최신 기능까지 지원할
  거라 가정하지 않고 실측해서 GPT/Solar를 1갈래로 합침(2026-08-07).
- **`app/pipeline/models.py`의 `get_model(provider, tier)`**: 모델 티어
  (LOW/MID/HIGH)를 provider별 실제 모델 ID로 매핑하는 곳을 한 곳으로 모음.
  작업 성격(단순 추출 vs 창의성 필요 vs 비교·판단)으로 먼저 정하고, 출력
  스키마가 바뀌면 재검증한다는 원칙(Step1에서 확인됨).
- **DB 저장**: `schedule_session.conditions`/`candidates`는 JSONB 컬럼 —
  파이프라인 스키마가 자주 바뀌는 시기라 마이그레이션 없이 대응하기 위함.
  Step2/3 중간 산출물을 위한 별도 컬럼은 없음(추후 필요 시 검토 대상).
- **async 파이프라인 함수 + DeepEval eval 테스트를 같이 쓸 때 주의할 점**
  (Step2 구현 중 실측으로 확인, Step3/4도 동일하게 적용될 것): `asyncio.wait_for`
  /`asyncio.timeout`은 DeepEval의 `GEval.measure()`가 내부적으로 거는
  `nest_asyncio` 패치와 상충한다 — 한 pytest 세션 안에서 `async def` 테스트
  함수가 이미 실행 중인 이벤트루프 위에서 `metric.measure()`를 부르면(내부적으로
  또 `loop.run_until_complete()`를 재진입), "RuntimeError: Timeout should be
  used inside a task"로 실패한다. 대응 2가지: (1) eval 테스트 함수는 Step1처럼
  **동기 `def`**로 두고 그 안에서 `asyncio.run(...)`으로 파이프라인 함수를
  호출할 것(테스트마다 새 이벤트루프가 생성·종료돼 재진입 문제가 안 생김).
  (2) 파이프라인 함수 자체도 `asyncio.wait_for`/`asyncio.timeout` 대신
  `concurrent.futures.Future.result(timeout=...)`로 타임아웃을 걸 것 — 어떤
  이벤트루프 상태에서 호출되든 영향받지 않아 더 안전하다(`generate_step2.py`의
  `_call_all_perspectives_sync` 참고).
