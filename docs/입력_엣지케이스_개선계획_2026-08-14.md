# 일정 조건 입력 — 엣지 케이스 개선 계획

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-08-14 |
| 범위 | 일정 생성 전 조건 입력(`ConditionWizardView`)과 `POST /schedules` 검증 |
| 상태 표기 | `⬜ 미착수` · `🟡 설계/확인 필요` · `✅ 완료` |

## 목적

사용자가 입력한 좋아요·싫어요, 시간, 인원, 예산 조건이 서로 충돌하거나 현실적으로
성립하지 않을 때, 조용히 무시하거나 파이프라인 실패로 끝내지 않고 입력 단계 또는
서버 검증 단계에서 이해 가능한 안내를 제공한다.

이 문서는 기능 구현 전 합의한 작업 목록이다. 아래의 **현재 동작**은 2026-08-14
코드 기준이며, **목표 동작**이 적용되기 전까지는 변경되지 않는다.

## 의도된 정상 동작 — 개선 대상 아님

다음은 오류가 아니라 서비스의 의도된 설계다.

| 상황 | 현재·유지할 동작 |
|---|---|
| `조용한 곳`, `분위기 좋은 곳`, `사람이 너무 많지 않은 곳` | 장소 데이터로 객관적으로 확인하기 어려운 소프트 취향이다. 추천에 참고하되 보장하지 않는다. |
| 좋아요가 전부 활동 취향<br>예: 방탈출·전시·보드게임카페 | 정상 입력이다. 좋아요가 음식일 필요는 없다. 일정 시간이 점심·저녁대를 포함하면 좋아요와 별개로 자연스러운 식사 장소를 포함하려 한다. |
| 좋아요·싫어요를 모두 비움 | 정상 입력이다. 목적·지역·시간·예산을 기준으로 일반 일정 후보를 생성한다. |
| 검색·필터 결과 전체 선택 | “나의 일정”에서 전체 선택은 현재 검색어·상태 필터 결과만 대상으로 한다. |
| 일괄 삭제에 타인 일정 ID 포함 | 서버는 삭제 전에 전 항목의 소유권을 검사한다. 하나라도 실패하면 아무 항목도 삭제하지 않는다. 이 원자적 동작을 유지한다. |

## 개선 항목

### 1. 좋아요·싫어요의 직접 충돌

**상태: ⬜ 미착수 / 우선순위: P0**

| 구분 | 내용 |
|---|---|
| 예시 | 좋아요: `초밥` / 싫어요: `초밥` |
| 현재 동작 | 입력 단계에서 충돌을 알리지 않는다. 정규화 뒤 좋아요·싫어요 태그 검색이 모두 수행되며, 싫어요 검색 결과에 해당한 장소는 후보 풀에서 제거된다. 결과적으로 싫어요가 사실상 우선되거나 후보 부족으로 생성이 실패할 수 있다. |
| 문제 | 사용자는 어느 조건이 우선됐는지 알 수 없다. |
| 목표 동작 | 제출 전에 충돌을 보여주고, 항목별로 `좋아요로 반영` / `싫어요로 제외` / `이번 일정에서 제외` 중 선택하게 한다. |
| 구현 메모 | 단순 원문 비교가 아니라 Step1 정규화 이후의 태그를 기준으로 판단한다. 선택 결과는 이후 조건 정규화·장소 검색에 일관되게 반영해야 한다. |
| 완료 기준 | 같은 태그를 양쪽에 입력했을 때 선택 UI가 나오며, 선택하지 않으면 일정 생성 요청을 보내지 않는다. |

### 2. 의미가 겹치는 좋아요·싫어요

**상태: 🟡 설계/확인 필요 / 우선순위: P1**

| 구분 | 내용 |
|---|---|
| 예시 | 좋아요: `초밥` / 싫어요: `해산물` |
| 현재 동작 | 문자열·검색 결과를 중심으로 필터링하므로 상·하위 개념이나 동의어 충돌을 확실히 판별하지 못한다. 결과가 남거나 제외되는 방식이 일관되지 않을 수 있다. |
| 목표 동작 | Step1이 충돌 가능성이 높은 태그 쌍을 반환하면, 사용자에게 “초밥은 해산물에 포함될 수 있어요”처럼 설명하고 우선 조건을 확인한다. |
| 구현 메모 | 모든 음식 지식 그래프를 직접 구축하지 않는다. Step1 구조화 출력에 `conflicts` 후보를 추가하거나, 별도 소규모 검증 호출로 처리할지 결정이 필요하다. |
| 완료 기준 | 대표적인 상·하위 개념 충돌을 확인 UI에서 처리하고, 사용자가 선택한 정책이 결과에 반영된다. |

### 3. 한 입력란 안의 부정 표현

**상태: ⬜ 미착수 / 우선순위: P1**

| 구분 | 내용 |
|---|---|
| 예시 | 좋아요 입력란에 `회는 빼고 파스타가 좋아요` 입력 |
| 현재 동작 | Step1 프롬프트가 부정 표현을 싫어요 태그로 분류하도록 지시하지만, 결과는 LLM 판단에 의존하며 화면에는 정규화 결과가 보이지 않는다. |
| 목표 동작 | 일정 요청 직전 요약 화면에 `반영할 좋아요`와 `제외할 것`을 태그 형태로 표시하고, 사용자가 잘못 분류된 항목을 수정할 수 있게 한다. |
| 구현 메모 | 충돌 확인 UI와 같은 “정규화 결과 확인” 단계로 합치는 것이 바람직하다. |
| 완료 기준 | 부정문이 어느 입력란에 있더라도 사용자에게 최종 분류 결과가 보인다. |

### 4. 너무 많은 선호 조건

**상태: ⬜ 미착수 / 우선순위: P1**

| 구분 | 내용 |
|---|---|
| 현재 동작 | 검색 가능한(verifiable) 좋아요·싫어요 태그는 각각 최대 5개만 반영된다. 초과 태그는 파이프라인에서 조용히 잘릴 수 있다. 주관적 태그는 검색 호출을 만들지 않아 이 상한과 별개다. |
| 문제 | 사용자가 적은 조건 중 무엇이 빠졌는지 알 수 없다. |
| 목표 동작 | 입력 화면에 “검색 가능한 중요 조건은 최대 5개 반영”을 안내하고, 정규화 확인 화면에서 실제 반영·미반영 항목을 표시한다. |
| 완료 기준 | 사용자는 생성 요청 전에 반영되는 검색 조건을 확인할 수 있다. |

### 5. 시간 범위의 서버 검증

**상태: ✅ 완료(2026-08-20) / 우선순위: P0**

| 구분 | 내용 |
|---|---|
| 예시 | 시작 18:00 / 종료 18:00, 또는 시작 19:00 / 종료 12:00 |
| 현재 동작 | 화면은 시작 시간이 종료 시간보다 앞설 때만 다음 단계로 진행하게 한다. 하지만 `POST /schedules` 요청 모델과 정규화 스키마에는 시간 순서를 재검증하는 명시적 validator가 없다. API 직접 호출 시 비정상 범위가 파이프라인까지 갈 수 있다. |
| 목표 동작 | 백엔드가 종료 시간이 시작 시간보다 늦은지 검증하고, 위반 시 422와 명확한 오류 문구를 반환한다. |
| 구현 메모 | 프런트 검증은 UX용으로 유지하고, 서버 검증을 진실의 원천으로 둔다. |
| 완료 기준 | UI 우회 요청도 시간 역전·동일 시간을 422로 거절한다. |

### 6. 자정을 넘기는 일정

**상태: 🟡 정책 결정 필요 / 우선순위: P2**

| 구분 | 내용 |
|---|---|
| 예시 | 22:00 ~ 다음 날 01:00 |
| 현재 동작 | 시간 문자열 비교상 종료 시간이 더 이르므로 화면에서 진행할 수 없다. 당일 일정만 지원한다. |
| 선택지 A | 당일 일정만 유지하고, 종료 시간이 다음 날인 일정은 아직 지원하지 않는다고 안내한다. |
| 선택지 B | `다음 날 종료` 토글 또는 날짜 입력을 추가하고, 파이프라인·경로 계산·식사 슬롯 계산을 날짜 경계까지 지원한다. |
| 완료 기준 | 선택한 정책에 맞는 안내 또는 생성 결과가 일관되게 제공된다. |

### 7. 인원·예산의 범위 검증

**상태: ⬜ 미착수 / 우선순위: P1**

| 구분 | 내용 |
|---|---|
| 현재 동작 | 프런트는 인원·예산이 0보다 큰지만 확인한다. 백엔드 요청 모델에는 최대값·정수·현실적 하한 검증이 없다. |
| 문제 | 매우 큰 인원, 소수 인원, 지나치게 낮거나 큰 예산이 파이프라인으로 전달될 수 있다. |
| 목표 동작 | 백엔드에서 인원은 정수 범위, 예산은 서비스 정책 범위로 검증하고 422를 반환한다. |
| 정책 결정 필요 | 정확한 허용 범위. 초기 제안: 인원 1~30명, 1인 예산 1,000~1,000,000원. |
| 완료 기준 | 화면·직접 API 요청 모두 같은 범위 규칙을 적용한다. |

### 8. 같은 제목의 일정 구분

**상태: ⬜ 미착수 / 우선순위: P2**

| 구분 | 내용 |
|---|---|
| 현재 동작 | 같은 이름의 일정 생성을 허용한다. “나의 일정” 검색도 제목 기준이므로 동일 제목을 구분하기 어렵다. |
| 목표 동작 | 이름 중복은 허용하되, 목록에 생성일·지역을 더 명확하게 보이고 자동 제목에는 날짜 등 구분 정보를 고려한다. |
| 완료 기준 | 동일 제목의 일정 두 개를 사용자가 목록에서 구분할 수 있다. |

### 9. 조건을 만족할 장소가 부족한 경우

**상태: 🟡 개선 가능 / 우선순위: P1**

| 구분 | 내용 |
|---|---|
| 현재 동작 | 후보 풀이 부족하면 409과 함께 생성 불가 응답을 돌려준다. 프런트는 해당 사유와 조정 가능한 조건을 보여줄 수 있다. |
| 문제 | 사용자가 무엇을 먼저 완화해야 하는지 충분히 구체적이지 않을 수 있다. |
| 목표 동작 | 지역·시간·필수 장소·선호 충돌 중 실제 병목에 따라 구체적인 완화 제안을 보여준다. |
| 완료 기준 | 생성 불가 화면에서 최소 한 가지 실행 가능한 다음 행동을 제공한다. |

## 권장 구현 순서

1. **P0** — 시간 범위의 백엔드 검증
2. **P0** — 좋아요·싫어요 직접 충돌 확인
3. **P1** — 정규화 태그 확인 화면(부정 표현·초과 조건·의미 충돌의 공통 기반)
4. **P1** — 인원·예산 서버 검증
5. **P1** — 생성 불가 사유별 완화 제안
6. **P2** — 자정 넘김 일정 정책 결정 및 구현
7. **P2** — 동일 제목 일정의 목록 구분 개선
