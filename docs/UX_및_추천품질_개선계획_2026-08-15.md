## 1. 반응형 — "나의 일정" 목록 카드 제목이 글자 단위로 줄바꿈

**상태: ✅ 완료 / 우선순위: P0**

| 구분 | 내용 |
|---|---|
| 파일 | `moduyaksok-frontend/src/views/ConfirmedSchedulesView.vue:192-231` |
| 원인 | 카드 한 행이 `flex flex-wrap` 안에 체크박스(`shrink-0`) · 제목 영역(`min-w-0 flex-1`) · 버튼 그룹(`shrink-0`) 3개를 한 줄로 배치한다. 좁은 화면에서 체크박스+버튼 그룹만으로 필요한 폭이 크고, `flex-wrap`이 걸려있어도 `min-w-0 flex-1`인 가운데 항목은 줄바꿈되지 않고 계속 눌려서, 결국 몇 px 폭까지 눌려 텍스트가 글자 단위로 줄바꿈된다. |
| 목표 동작 | 좁은 화면에서는 체크박스, 제목(전체 너비), 버튼 그룹이 각자 자기 줄에서 자연스럽게 쌓인다. |
| 구현 메모 | 카드 내부 컨테이너를 `flex-col sm:flex-row`로 바꾸거나, 제목 블록에 `basis-full sm:basis-auto`를 줘서 좁은 화면에서 항상 자기 줄을 차지하게 한다. 체크박스+뱃지 한 줄 → 제목 한 줄 → 버튼 그룹 한 줄 순서로 쌓이는 게 자연스럽다. |
| 완료 기준 | 375~430px 폭에서 제목이 단어 단위로 줄바꿈되고 체크박스·버튼과 안 겹침. |

## 2. 반응형 — 조건 입력 마법사 종료 시간 인풋이 화면 밖으로 밀림

**상태: ✅ 완료 / 우선순위: P0**

| 구분 | 내용 |
|---|---|
| 파일 | `moduyaksok-frontend/src/views/ConditionWizardView.vue:143-146` |
| 원인 | `<div class="flex gap-3">` 안에 `DoodleInput`(`type="time"`) 두 개가 `flex-1`만 걸려있고 `min-w-0`가 없다. flex item의 기본 `min-width: auto`는 내용물의 최소 콘텐츠 크기를 존중하는데, 네이티브 `<input type="time">`은 로캘(오후 09:00 같은 한국어 AM/PM 포맷)에 따라 내재적 최소 폭이 꽤 커서, 두 인풋이 `flex-1`로 줄어들려 해도 그 최소 폭 밑으로는 못 줄어들어 합이 컨테이너 폭을 넘고 오른쪽 인풋이 화면 밖으로 밀린다. 전형적인 "flex item 오버플로" 버그. |
| 목표 동작 | 두 인풋이 컨테이너 폭 안에서 균등하게 줄어들고 화면 밖으로 안 밀림. |
| 구현 메모 | `class="flex-1"` → `class="flex-1 min-w-0"`로 변경. `DoodleInput` 내부 `<input>`은 이미 `w-full`이라 부모가 줄면 같이 준다. |
| 완료 기준 | 320~430px 폭에서 두 인풋 모두 화면 안에 온전히 보임. |

## 3. 반응형 — 일정 생성 완료 토스트가 부자연스럽게 왼쪽에 쏠림

**상태: ✅ 완료 / 우선순위: P1**

| 구분 | 내용 |
|---|---|
| 파일 | `moduyaksok-frontend/src/App.vue:84` |
| 원인 | 토스트 컨테이너가 `w-[min(22rem,calc(100vw-2.5rem))]`로 **고정 너비**다. 데스크톱에서는 22rem으로 적당히 좁지만, 모바일에서는 `100vw-2.5rem`(거의 풀스크린)이 선택돼 박스 자체가 화면 폭 대부분을 차지한다. 안의 내용(한 줄 메시지 + 버튼 하나)은 왼쪽 정렬이라, 넓은 박스 안에서 왼쪽에만 몰려 있고 오른쪽에 불필요한 여백이 남아 "쏠려 보이는" 것. |
| 목표 동작 | 박스가 내용 크기에 맞게 좁아지되, 화면보다 넓어지지 않는 상한만 유지. |
| 구현 메모 | `w-[min(22rem,calc(100vw-2.5rem))]` → `w-fit max-w-[min(22rem,calc(100vw-2.5rem))]`로 변경 — 너비를 고정하지 않고 콘텐츠 기준 + 상한만 건다. |
| 완료 기준 | 모바일 폭에서 토스트가 텍스트 길이에 맞게 좁게 뜨고 우측에 부자연스러운 여백이 안 남음. |

## 4. 자차·대중교통 경로 정보가 요즘 자주 안 나오는 문제

**상태: ✅ 완료 / 우선순위: P0**

사용자 피드백: "로그는 사용자한테 안 보이는 게 맞지만, 실제로 백엔드 로그·교통편별 결과를 보면 경로 찾기 자체가 실패하는 경우가 많다" — 아래는 이 지적을 받고 직접 실측한 결과.

| 구분 | 내용 |
|---|---|
| 조사 결과 (1) | NCP Maps(자차) 호출엔 ODsay(대중교통)와 달리 예산/레이트리밋 게이트가 전혀 없다(`enrich_step4.py`의 `fetch_car()`, `rate_limiter.py`에 관련 키 없음, 2026-08-13 변경이력에 "NCP Maps는 별도 한도 요청이 없어 그대로 둠"으로 명시). |
| 조사 결과 (2) | 재시도 로직이 없다(`naver_directions.py:58-62`, `httpx.AsyncClient(timeout=10.0)` 1회 호출, 실패 시 바로 `NaverDirectionsError`). 일시적 네트워크 hiccup 한 번이면 그 구간의 자차 옵션은 그냥 사라진다. |
| 조사 결과 (3) | 오늘 이 세션에서 커밋한 `e0995cd`가 자차/대중교통 실패 시 사용자에게 보이던 경고 문구를 제거했다 — 실패율 자체가 아니라 "왜 없는지 설명이 없어서" 더 눈에 띄게 된 부분도 여전히 유효한 요인이다. |
| **실측 (오늘 직접 확인)** | ① `naver_local_search.py`의 mapx/mapy→위경도 변환이 API Hub 이관 후에도 깨졌는지 의심했으나, 실제 검색 결과 3건 모두 정상적인 한국 좌표로 확인 — **이 경로는 원인이 아님**. ② Redis에 저장된 오늘자 일일 호출 카운터를 직접 조회: `odsay:daily_count`=20/1000, `naver_search:daily_count`=55/25000 — **예산 소진도 지금은 원인이 아님**. ③ 잠실 인근 실제 좌표 3쌍(가까운 거리·먼 거리 섞음)으로 `get_car_option()`/`get_transit_options()`를 직접 호출 — **3/3 전부 정상 성공**(자차 10~18분, 대중교통 11~22개 옵션). 지금 이 순간은 재현이 안 됨. |
| **구조적 결함 발견 — 진짜 원인일 가능성** | `odsay_directions.py:124-130`: `if body.get("error") is not None: return []` — ODsay가 에러 응답을 주면(700m 이내처럼 정상적인 "무경로"든, 인증 오류·일시 장애 같은 **진짜 실패**든) **구분하지 않고 똑같이 빈 리스트로 처리한다.** 코드 주석에 "API 응답만으로 구분할 수 없어 페일세이프하게 처리"라고 의도적으로 설계돼 있음. 문제는 이 경로가 예외를 던지지 않아 `logger.exception`도 안 찍힌다는 것 — **진짜 API 실패가 나도 로그에 전혀 흔적이 안 남는다.** 사용자가 "로그를 보니 실패가 많다"고 한 게 이 경로라면, 지금은 원인(네트워크? 인증? ODsay 장애?)을 로그만으로 구분할 방법이 아예 없다. |
| 목표 동작 | (a) 일시적 네트워크 hiccup에 대한 복원력을 높인다, (b) "진짜 API 실패"·"700m 이내 정상 무경로"·"기타 무경로"를 로그에서 셋 다 구분 가능하게 만든다, (c) 700m 이내라 대중교통·자차 정보가 없는 건 사용자에게도 자연스럽게 hedge 안내한다(사용자 추가 요청 반영). |
| 구현 메모 — 로그 | ① `naver_directions.py`/`odsay_directions.py` 둘 다 짧은 재시도(1회, 백오프 없음) 추가. ② `odsay_directions.py:104`의 클라이언트 사이드 700m 사전 체크(`haversine_distance_m(...) < 700: return []`)에 `logger.info("transit_skip_too_close ...")`를 추가해 지금은 무로그였던 "정상 스킵"도 백 로그에 남긴다. ③ API를 실제로 호출한 뒤 `error` 응답을 분기: `error.code == "-98"`(ODsay 자체 판단 700m 이내)도 같은 info 로그로, **그 외 에러 코드는 `logger.warning`으로 code/message를 남긴 뒤 여전히 `[]`로 degrade**(사용자 경험은 안 바꾸되 관측 가능하게). |
| 구현 메모 — 사용자 안내 | ④ `naver_directions.py`의 자차 쪽에는 700m 전용 규칙이 없음(NCP는 자체적으로 code!=0 판단) — 그래서 "700m 이내" 여부는 **`enrich_step4.py`가 이미 갖고 있는 `a.lat/a.lng/b.lat/b.lng`로 직접** `haversine_distance_m()`을 호출해 판단한다(제공자 함수를 안 바꾸고 오케스트레이션 레이어에서 같은 공식을 재사용 — 최소 변경). 이 값이 700m 미만이고 해당 구간의 최종 `options`가 도보뿐이면, 구간마다 반복해서 경고를 붙이지 않고 **`enrich_routes()`가 반복문을 다 돈 뒤 한 번만** "일부 구간은 걸어가기 좋은 가까운 거리라 대중교통·자차 정보는 따로 안 보여드려요" 같은 hedge 문장을 `feasibility_warning`에 추가한다(사용자 요청대로 "그런 케이스가 발생한 후보에서 공통으로 1회 표시"). |
| 완료 기준 | 에러 코드가 로그에 남아 "700m 이내 정상", "기타 정상 무경로", "실제 실패"를 구분할 수 있게 되고, 700m 이내 구간이 있는 후보는 사용자에게도 자연스러운 안내가 뜨며, 재시도 추가 후 일시적 네트워크 실패로 인한 옵션 소실이 줄어듦. |
| 한계 | 지금 이 순간 실제 API 호출로는 재현이 안 돼서 "얼마나 자주" 진짜 실패가 나는지는 로그 구분 개선 없이는 확인 불가 — 로그 분기부터 넣고 다음 발생을 기다리는 게 가장 빠른 다음 단계. |

## 5. 카테고리에 "공원" 추가 (한강공원 등 탐색 가능하게)

| 구분 | 내용 |

| 목표 동작 | "공원 가고 싶어요" 같은 입력이 정확히 분류되고, Step2가 "{지역} 공원"으로 검색해 한강공원 등을 후보 풀에 포함시키며, 프런트도 전용 아이콘으로 보여줌. |

| 완료 기준 | "한강공원 가고 싶어요" 입력이 verifiable=true/place_type으로 분류되고, 실제 일정에 공원 장소가 등장하며 전용 아이콘으로 표시됨. |

## 6. 태그 조건이 너무 빡빡해서 "결과 없음"이 자주 뜸

**상태: ✅ 완료 / 우선순위: P0**

| 구분 | 내용 |
|---|---|
| 예시 | 잠실 + `와플, 한강공원, 닭갈비, 플스방`(4개) 또는 `와플, 닭갈비, 플스방`(3개) → 결과 없음 |
| 조사 결과 | `generate_algorithm_step2.py` / `generate_step2.py` / `synthesize_step3.py` 세 곳에 동일한 `min(verified_count // 2 + 1, feasible_count)` 과반수 규칙이 중복돼 있다. verifiable 태그 1~5개 기준 요구 충족 수는 1,2,2,3,3 — 사용자가 짐작한 "1/1/1/2/2"와 정확히 같진 않지만, 같은 계열의 엄격한 다수결 규칙이다. 더 결정적으로, `generate_step2.py`의 `_can_assign_distinct_tags`는 특정 태그의 검색 결과(`place_candidates`)가 0건이면 그 태그를 요구하는 조합 자체를 하드 실패시킨다 — "잠실 플스방" 검색이 0건이면, 그 태그를 쓰는 조합은 관점(perspective) 3개 전부에서 무너지고, 셋 다 실패하면 최종적으로 완전한 "결과 없음"(`_infeasible_response()`)이 된다. |
| 목표 동작 | 엄격한 기준을 만족하는 조합이 하나도 없어도 그대로 실패시키지 말고, 기준을 단계적으로 완화해 최소 1개 이상은 항상 나오게 한다(사용자 요청 그대로). |
| 구현 메모 | ① 세 곳에 중복된 `min(count//2+1, feasible_count)` 계산을 공용 함수로 먼저 통합(완화 로직을 한 곳에서만 관리하기 위한 선행 작업). ② 필터링을 "요구 커버리지 자동 완화 루프"로 감싼다: 과반수+1 기준 시도 → 생존 0이면 요구치를 1씩 낮춰 재시도 → 그래도 0이면 태그 앵커 하드 요구(`_can_assign_distinct_tags`)도 완화 → 그래도 0이면 verifiable 태그 요구 자체를 없애고 일반 후보로 폴백. ③ 완화가 발생하면 침묵하지 말고 `feasibility_warning`에 "태그 조건을 일부 완화해서 찾았어요" 같은 hedge 안내를 반드시 남긴다(조용히 봐주면 사용자가 왜 태그가 안 지켜졌는지 모름). ④ 완화 발동 여부·최종 채택 요구치를 로그로 남겨 실제 발동 빈도를 추후 확인 가능하게. |
| 설계 메모 | ponytail 원칙대로 가장 얕은 것부터: "요구치를 단계적으로 낮추는 루프"만 우선 구현하고, 그래도 0건이면 앵커 요구를 드롭 — 완전한 조합 백트래킹까지는 가지 않아도 대부분 케이스가 해결될 것으로 예상. 백트래킹이 실제로 더 필요한지는 이 얕은 버전을 실측한 뒤에 판단. |
| 완료 기준 | "와플, 한강공원, 닭갈비, 플스방" 조합이 잠실에서 완전한 결과 없음 대신, 어떤 태그가 빠졌는지 안내와 함께 최소 1개 이상의 완화된 후보를 반환. |

## 7. 후보 결과 화면에서 네이버 지도로 장소 직접 검색해 추가

**상태: ✅ 완료 / 우선순위: P2**

사용자 제안: "네이버 지도 딥링크 왕복 대신, 사용자가 준 주소·식당명을 바로 우리 API에 넣으면 안 되나?" — 실제로 호출해서 확인.

| 구분 | 내용 |
|---|---|
| 요청 흐름 | "3개의 일정이 나왔어요" 화면(`CandidatesView.vue`)의 좋아하는 태그 항목 옆 "+" 버튼 → 장소 이름/주소 입력 → "내가 추가한 장소" 카테고리에 등록(최대 3개, 기본 이름은 입력값, 수정 가능) → "일정에 추가" + "재생성"으로 반영. |
| 기존 재사용 가능 인프라 | `RequiredPlace` 스키마(`schemas.py:319-326`)가 "후보 풀에서 고른, 재생성 시 반드시 포함할 장소 스냅샷"을 이미 구현하고 있다 — place_id/name/category/address/map_url 필드에 재생성 강제 반영 로직까지 있어 이 기능과 목적이 거의 같다. |
| **실측: 기존 검색 API를 지오코딩으로 재사용 가능한가** | `app/services/naver_local_search.py`의 `search_places()`에 사용자가 입력할 법한 텍스트를 그대로 넣어 실제로 호출해봤다. 결과: **식당명("스타벅스 잠실역점")과 "랜드마크+지역"("한강공원 잠실")은 정확한 결과 + 좌표(mapx/mapy)를 바로 돌려줌** — 별도 지오코딩 API 없이 기존 검색 함수 재사용만으로 충분함. 반면 **순수 도로명주소만 입력하면("서울 송파구 올림픽로 300") 결과 0건** — 이 API는 업체/장소 검색이지 범용 주소 지오코더가 아니라서다. |
| **결론 — 네이버 지도 딥링크 왕복 없이 바로 처리 가능** | 사용자가 "네이버 지도에서 검색해서 복사해오기"를 거칠 필요 없이, **프런트에서 바로 장소 이름을 입력받아 백엔드가 `search_places(query)`로 조회 → 상위 결과(들)를 보여주고 사용자가 확인/선택**하는 흐름으로 단순화할 수 있다. 자동완성 검색창에 가깝게 만들 수 있음 — 딥링크·복붙 왕복, 별도 지오코딩 API 계약 둘 다 불필요. 다만 순수 주소만 입력하는 사용자는 결과가 안 나올 수 있으니, 안내 문구("가게 이름이나 근처 랜드마크로 검색해보세요")와 빈 결과 처리(재시도 유도)는 필요. |
| **검색 결과가 0개/1개/여러 개일 수 있다는 지적** | 맞다 — 사용자가 부정확하게 입력하면 0건, 흔한 상호명("스타벅스")이면 여러 지점이 나올 수 있다(실측에서도 "스타벅스 잠실역점" 검색에 근처 지점이 여러 개 나옴). 그래서 검색은 **선택 단계가 필수**고, 사용자 제안대로 새 팝업 모달로 처리하는 게 맞다. |
| **UI 설계 — 새 모달** | 기존 `LoginModal.vue`가 이미 쓰고 있는 `DoodleModal`(`open`/`title` props, `close` emit, 슬롯 기반 — 새로 만들 것 없이 그대로 재사용 가능)을 그대로 쓴다. 흐름: "+" 버튼 클릭 → `DoodleModal` 오픈 → 검색어 입력창 + "검색" 버튼 → 결과 0건이면 "장소를 찾지 못했어요. 가게 이름으로 다시 검색해보세요" 안내 + 재검색, 1건 이상이면 `CandidatesView.vue`가 이미 쓰는 장소 리스트 카드 패턴(이름/카테고리/주소, `.name`/`.category`/`.address`)을 재사용해 목록으로 보여주고 **사용자가 카드를 탭해서 선택**(라디오처럼 하나만 선택 가능) → 선택 즉시 "내가 추가한 장소" 목록에 반영 + 모달 닫힘. |
| **"+" 버튼 위치** | `CandidatesView.vue:209` 각 좋아요 태그 `<summary>{{ group.label }} · {{ group.places.length }}곳</summary>` 줄 옆에 작은 "+" 버튼 — "이 태그를 만족하는 곳을 직접 추가하고 싶다"는 맥락에 맞게 태그 그룹 단위로 붙인다. |
| **기존 인프라 재사용 시 놓쳤던 제약 — 재조사 필요했던 부분** | `RequiredPlace`를 그대로 쓰면 될 줄 알았는데, `generate_step2.py:823`에 `if not set(required_place_ids).issubset({_place_id(place) for place in places}): return []`라는 하드 체크가 있다 — **재생성마다 새로 돌리는 카테고리·태그 검색 결과(`place_candidates`)에 그 place_id가 실제로 들어있어야만** 그 클러스터가 살아남는다. 사용자가 검색한 "스타벅스 잠실역점"은 표준 카테고리(15개)·태그 검색 쿼리에 우연히 안 걸리면 재생성 때 place_candidates에서 빠지고, 이 subset 체크에 걸려 **해당 클러스터 전체가 조용히 드롭된다** — 최악의 경우 6번 항목과 같은 종류의 "결과 없음"으로 이어질 수 있다. 즉 `RequiredPlace`에 필드만 추가하는 걸로는 부족하고, **place_candidates 조립 단계 자체를 건드려야 한다.** |
| 구현 메모 | ① `RequiredPlace`에 `is_custom: bool = False`와 좌표 보존용 필드(`mapx`/`mapy` 원본 문자열, 기존 `_coords()` 파싱 함수를 그대로 재사용하기 위해 이미 검증된 포맷 그대로 저장) 추가. category는 고정 문자열("직접 추가"). ② 백엔드에 "이름으로 장소 검색" 소형 엔드포인트 추가 — `search_places(query, display=5)`를 그대로 호출해 후보 목록(이름/주소/좌표 포함 원본에 가까운 dict)을 반환. ③ **`orchestrate.py:136-137`(`place_candidates = ensure_place_ids(await search_places_for_region(...))`) 직후, is_custom=True인 required_places의 원본 place dict를 `place_candidates`에 append** — 표준 검색 쿼리로 못 찾은 장소도 항상 풀에 존재하게 만들어 위 subset 체크를 자연히 통과시킨다(신규 필터링 로직 없이, 이미 있는 "place_candidates에 있으면 통과"라는 기존 규칙을 그대로 타게 만드는 게 가장 적은 변경). ④ 프런트: "+" 버튼 → 모달(검색 → 리스트 → 탭 선택) → "내가 추가한 장소" 목록 반영, 이미 3개면 버튼 비활성화 + 안내. ⑤ 최대 3개 제한은 서버(POST 시 `is_custom=True` 개수 검증, 초과 시 400)와 프런트 UI 양쪽에서 이중 강제. |
| 완료 기준 | 검색 결과가 0/1/N건 모두 자연스럽게 처리되고, 사용자가 고른 장소가 표준 카테고리·태그 검색에 안 걸리는 곳이어도 재생성 시 후보에서 조용히 드롭되지 않고 반드시 포함됨. |
