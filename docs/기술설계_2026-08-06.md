## 1. 전체 아키텍처

```
[Vue 3 SPA] ── REST/JSON ──> [FastAPI 서버] ── SQL ──> [Postgres]
                                   │
                                   ├─ Google OAuth 검증
                                   ├─ AI 파이프라인 (LLM 호출: 사용자 API 키 or 개발용 env 키)
                                   └─ ODsay 대중교통 길찾기 API (경로/이동시간/교통비 — 원래 네이버
                                      지도 API 예정이었으나 NCP가 신규 가입을 막아 카카오모빌리티를
                                      거쳐 ODsay로 변경, 2026-08-09)
```

- 프론트/백엔드 분리 배포 (Vue → Vercel/Netlify 정적 호스팅, FastAPI → Railway/Render)
- 백엔드는 단일 FastAPI 앱. 파이프라인은 별도 오케스트레이션 프레임워크 없이 plain async 함수로 구성 (분기/재시도가 복잡해지면 그때 도입 검토)

## 2. 로그인 방식 — Google OAuth 2.0

### 2.1 플로우 (Authorization Code, 프론트 주도)

1. 사용자가 "Google로 로그인" 클릭 → Vue에서 Google OAuth 동의 화면으로 리다이렉트 (`@react-oauth/google` 계열 대신 Vue는 구글 공식 JS SDK 또는 `vue3-google-login` 사용)
2. Google이 `id_token`(JWT)을 프론트로 반환
3. 프론트가 `id_token`을 FastAPI `POST /auth/google`로 전달
4. 백엔드가 Google의 공개키로 `id_token` 서명 검증 (`google-auth` 라이브러리의 `id_token.verify_oauth2_token`) → 자체 서버가 Google과 별도로 토큰을 발급받는 절차(클라이언트 시크릿 교환) 불필요, 검증만 하면 됨
5. 검증 성공 시 `email`, `google_id`, `name` 추출 → `users` 테이블에 upsert
6. 백엔드가 **자체 세션 JWT** 발급 (access token, 만료 1~2시간) → 프론트는 이후 요청에 `Authorization: Bearer <token>` 헤더로 전달
7. 리프레시는 단순하게: 만료되면 프론트가 재로그인 유도 (refresh token 회전 로직은 MVP에서 생략, 필요해지면 추가)

### 2.2 왜 이 방식인가
- 비밀번호 저장/해싱/재설정 플로우를 통째로 생략 (요청하신 "로그인은 직접 안 하고 싶다"에 부합)
- 백엔드는 Google과 OAuth 코드 교환을 직접 할 필요 없이 **프론트에서 받은 id_token만 검증**하면 되므로 구현이 가장 짧음 (Google Identity Services의 "One Tap / Sign In With Google" 표준 패턴)

### 2.3 DB 스키마

```python
class User(SQLModel, table=True):
    id: UUID = Field(primary_key=True, default_factory=uuid4)
    google_id: str = Field(unique=True, index=True)
    email: str
    name: Optional[str] = None
    created_at: datetime = Field(default_factory=datetime.utcnow)
```

### 2.4 세션 검증 의존성 (FastAPI)

```python
async def get_current_user(
    token: str = Depends(oauth2_scheme),
    session: Session = Depends(get_session),
) -> User:
    payload = jwt.decode(token, SECRET_KEY, algorithms=["HS256"])  # 자체 서명 세션 JWT
    user = session.get(User, payload["sub"])
    if not user:
        raise HTTPException(401)
    return user
```

비로그인 상태로도 서비스 체험은 가능하게 할지(예: 로그인 없이 일정 생성 1회 체험 후 로그인 유도) 여부는 정책 결정 사항 — 지금은 **모든 일정 생성 API는 로그인 필수**로 가정하고, 게스트 체험이 필요해지면 `get_current_user`를 `get_current_user_optional`로 바꾸는 정도의 변경이면 됨.

## 3. API 키 관리 (BYOK) + 개발용 환경변수

### 3.1 원칙
- 사용자는 API 키 등록 전 **AI 제공자(Claude 또는 GPT)를 먼저 선택**한다. 계정당 등록 가능한 키는 1개(제공자 변경 시 기존 키는 삭제 후 재등록).
- **운영/실사용**: 사용자가 선택한 제공자의 API 키를 로그인 후 등록 → 그 키로 본인의 LLM 호출 과금
- **개발/테스트**: 개발자 본인의 Claude API 키를 `.env`로 넣어 로컬에서 파이프라인 테스트 → 이 값은 실제 서비스 로직과 분리된 "폴백"이 아니라 순수 개발 편의용 (제공자는 anthropic 고정)

### 3.2 우선순위 로직 (키 조회 함수 하나로 통일)

```python
def resolve_credential(user: Optional[User], session: Session) -> tuple[str, str]:
    """(provider, api_key) 튜플 반환"""
    if user:
        cred = session.exec(
            select(LLMCredential).where(LLMCredential.user_id == user.id)
        ).first()
        if cred:
            return cred.provider, decrypt(cred.encrypted_key)
    if settings.dev_fallback_api_key:  # .env의 ANTHROPIC_API_KEY, ENV=development일 때만 사용
        return "anthropic", settings.dev_fallback_api_key
    raise HTTPException(400, "API 키가 등록되지 않았습니다.")
```

- `provider`에 따라 파이프라인에서 Anthropic SDK 또는 OpenAI SDK 클라이언트를 선택해 생성 (`build_llm_client(provider, api_key)`)
- `dev_fallback_api_key`는 `ENV=development`일 때만 읽도록 설정 로더에서 분기 → 실수로 운영에 개발자 개인 키가 쓰이는 사고 방지

### 3.3 DB 스키마

```python
class LLMCredential(SQLModel, table=True):
    id: UUID = Field(primary_key=True, default_factory=uuid4)
    user_id: UUID = Field(foreign_key="user.id", unique=True)
    provider: Literal["anthropic", "openai"]  # 등록 시 필수 선택, 기본값 없음
    encrypted_key: bytes
    verified_at: Optional[datetime] = None  # 등록 시 ping 검증한 시각
    created_at: datetime = Field(default_factory=datetime.utcnow)
```

- 암호화: `cryptography.fernet.Fernet`, 마스터키는 `.env`의 `CREDENTIAL_ENCRYPTION_KEY` (운영에서는 시크릿 매니저)
- 키 등록 API(`POST /me/llm-credential`)는 저장 전 가벼운 검증 호출(예: 짧은 모델 호출 1회) 후 성공 시에만 저장

### 3.4 키 저장 위치 논의 — 서버 운영자 신뢰 문제 (2026-08-07)

**문제 제기**: 지금 구조는 서버(`.env`의 `CREDENTIAL_ENCRYPTION_KEY`)가 있으면 DB의
어떤 사용자 키든 복호화할 수 있다. 즉 "DB 유출"뿐 아니라 "서버 운영자가 직접
들여다봄"도 기술적으로 막을 수 없다 — 사용자 입장에서 신뢰 문제가 될 수 있음.

**검토한 대안 3가지**:

| 방식 | 신뢰 문제 해결 | 비용/리스크 |
|---|---|---|
| A. 완전 클라이언트 사이드 (브라우저가 provider 직접 호출) | 완전 해결 — 서버가 키를 아예 못 봄 | Step1~4 로직·프롬프트가 프런트에 노출, provider별 CORS 확인 필요, 개발 비용 큼 |
| B. 서버는 조율만, 키는 저장 안 함 (요청마다 프런트가 전달) | 저장 시점 문제는 해결, 여전히 요청 처리 중엔 서버가 봄 | 중간 |
| C. PIN 기반 envelope encryption (KDF로 PIN→키 조각 유도, 서버 마스터키와 합성) | 거의 해결 — 서버 혼자선(PIN 없이) 복호화 불가 | 중간. PIN 분실 시 키 영구 복구 불가(재등록 안내 필요) |

각 대안 모두 "저장 위치를 서버 DB에서 사용자 브라우저(`localStorage`)로 옮기면
해결"이라는 생각이 들 수 있는데, 이건 문제를 없애는 게 아니라 **바꾸는 것**이다 —
`localStorage`는 페이지에서 실행되는 어떤 JS든(정상 코드든 XSS든) 읽을 수 있어서,
서버 쪽 유출 리스크를 "우리 프런트에 XSS 취약점 하나만 있으면 전 사용자 키가
한 번에 털리는" 리스크로 바꾸는 셈. 서버 인프라 하나를 지키는 것보다 사용자마다
브라우저 보안까지 다 책임지는 쪽이 공격 표면이 더 넓다고 판단.

**결정**: 지금 단계(실사용자 없음, 1인 개발)에선 **구조를 바꾸지 않는다.** 대신
저비용 완화책만 적용:
- 복호화 이벤트 감사 로그 (누가/언제, 값은 남기지 않음)
- API 키 등록 화면에 provider 측 사용량 제한(spending limit) 설정 안내
- 실사용자 받는 시점에 개인정보처리방침 등에 이 구조적 한계를 명시

**나중에 구조를 바꿔야 할 때를 대비한 메모**: 지금 파이프라인 함수(`normalize_conditions`
등)가 `api_key: str`을 이미 복호화된 평문으로 파라미터로 받도록 설계돼 있어서 —
"어떻게 저장/복호화했는지"와 "그 키로 뭘 하는지"가 분리돼 있음. 그래서 나중에
C안(PIN 기반)으로 옮겨도 `app/models/llm_credential.py`, `app/services/credential.py`,
`app/routers/credential.py`, 프런트 API 키 등록 화면 정도만 건드리면 되고
**`app/pipeline/*.py`는 안 바뀐다.** A안(완전 클라이언트 사이드)은 이 재사용이
안 되고 훨씬 큰 재작업.

## 4. AI 에이전트 파이프라인 (단계별 상세)

프레임워크(LangGraph, CrewAI 등) 없이 **plain async 함수 체인**으로 구성. 각 단계는 Pydantic 모델을 입출력으로 강제해 정확성을 담보.

```
[요청 입력]
   │
   ▼
Step 1. 조건 정규화 (normalize_conditions)
   │
   ▼
Step 2. 후보 생성 — Fan-out (generate_candidates)  ← MoA "Proposer" 단계
   │  (N=3개의 서로 다른 프롬프트/temperature로 병렬 LLM 호출)
   ▼
Step 3. 검증·병합 (synthesize_and_validate)  ← MoA "Aggregator" 단계, 랭킹 없이 동등한 3개 확정
   │
   ▼
경로 없는 후보 3개 응답 (ScheduleResponse) ── 여기까지가 POST /schedules 1번 호출
   │
   ▼  (사용자가 3개 중 하나를 선택)
Step 4. 이동 동선 보강 (enrich_routes)  ← ODsay 대중교통 길찾기 API, 선택된 후보 1개에만 실행
   │
   ▼
최종 1안 응답(경로 포함)
```
**왜 검증·병합(Step3)이 이동 동선 보강(Step4)보다 먼저인가(2026-08-10 재설계 —
원래는 이동 동선 보강이 먼저였고 번호도 반대였는데, 실행 순서에 맞춰 두 단계의
번호 자체를 스왑했다)**: Step3는 Step2의 장소·시간 데이터만으로 검증 가능하고
(경로 데이터 불필요), Step4(ODsay 호출)만 후보마다 비용이 든다. 사용자는 결국
3개 중 1개만 볼 텐데 3개 전부에 미리 경로를 조회하면 낭비다 — Step4를 사용자
선택 뒤로 미뤄서 실제로 열어볼 후보 1개분만 호출한다. 이 때문에 파이프라인이
한 요청 생명주기가 아니라 두 번의 API 호출로 나뉜다. 상세 근거·DB 저장 지점
논의는 `docs/AI파이프라인_Step별_설계_2026-08-09.md` "전체 흐름" 절 참고.

### Step 1. 조건 정규화 — `normalize_conditions()`
- 입력: `POST /schedules` 요청 바디 그대로 (목적/인원/시간/지역/예산은 프런트에서
  이미 구조화해서 보냄, `liked_text`/`disliked_text`만 자유 텍스트 — 각 최대 100자.
  프런트는 태그 선택 UI가 아니라 자유 텍스트 입력이라, 여기서 처음으로 구조화됨)
- 처리: `liked_text`/`disliked_text`(예: "해산물 빼고 조용한 데")를 LLM 호출 1회로
  구조화 태그 배열로 변환. 나머지 필드는 이미 구조화돼 있으니 그대로 통과
- 출력 (Pydantic):
```python
class PreferenceTag(BaseModel):
    tag: str
    verifiable: bool  # 장소 카테고리 데이터로 확인 가능한 객관적 태그인가

class NormalizedConditions(BaseModel):
    purpose: Literal["date", "friends", "family", "party", "other"]
    headcount: int
    time_range: tuple[datetime, datetime]
    regions: list[str]  # 최대 3개, 시/도만인 항목은 최대 1개
    liked_tags: list[PreferenceTag]
    disliked_tags: list[PreferenceTag]
    budget_per_person: int
```
- **`verifiable` 구분(2026-08-07 결정)**: "해산물"은 장소 카테고리/메뉴로 나중에
  검증 가능하지만, "사람 많은 곳"처럼 장소 데이터에 없는 주관적 취향은 검증할
  방법이 없음. Step1이 각 태그를 verifiable(True/False)로 분류해서 Step2에 넘기면,
  Step2가 True는 하드 제약(확실히 반영)으로, False는 소프트 신호(참고만, 보장
  안 함)로 다르게 취급할 수 있음 — 검증 불가능한 걸 검증한 것처럼 확신하지 않기
  위한 설계 (자세한 사용 방식은 Step2 문단 참고)
- 실패 처리: 필수 필드 누락 시 이 단계에서 즉시 400 반환 (LLM 호출까지 가지 않음 — 비용 절약)
- 보안: `liked_text`/`disliked_text`가 사용자 자유 입력 그대로 프롬프트에 들어가므로
  프롬프트 인젝션 가능성 있음. structured output으로 출력 스키마를 강제하면 "다른
  텍스트를 출력하게" 만들 수는 있어도 이후 파이프라인 흐름 자체를 바꾸진 못함
- **프롬프트 설계**: 추출/분류 작업이라 CO-STAR 같은 콘텐츠 생성용 프레임워크보다
  RTF(Role/Task/Format) 뼈대 + few-shot이 더 맞는다고 판단(2026-08-07). 특히
  few-shot 예시 4개 중 하나는 실제 관측된 실패(빈 입력에 없는 지명·음식을
  지어내는 할루시네이션)를 그대로 예시로 박아 직접 겨냥함 (`normalize_step1.py`
  `_SYSTEM_PROMPT` 참고). Step3의 `why_recommended`처럼 톤·설득력이 중요한
  창의적 글쓰기 단계에는 CO-STAR가 나중에 더 맞을 수 있음

### Step 2. 후보 생성 (Proposer, Fan-out) — `generate_candidates()`
- 입력은 Step1이 만든 `NormalizedConditions` **한 세트뿐**. 이 하나의 조건을 가지고
  `asyncio.gather`로 서로 다른 관점의 프롬프트 N=3개를 **동시에(병렬)** 호출 —
  3개의 서로 다른 조건을 넣는 게 아니라, 같은 조건을 3번 다른 관점으로 물어보는
  것 (`resolve_credential()`로 얻은 provider에 따라 Claude/GPT/Solar 클라이언트 사용,
  모델 성능은 MID 티어 — `app/pipeline/models.py`)
  - 예: (a) "실내 중심, 가성비 우선" (b) "동선 최소화 우선" (c) "사용자 취향 태그 최대 반영"
  - **왜 3번 따로 호출하나 (1번 호출로 "다른 후보 3개 줘"라고 안 하는 이유)**: 단일
    프롬프트 반복 호출은 결국 하나의 추론 흐름에서 나온 결과라 겉보기만 다르고
    구조적으로 비슷해지기 쉬움. 관점 자체를 프롬프트 레벨에서 다르게 박아 독립
    호출하면 실질적으로 차별화된 결과가 나옴 (기능명세서 요구사항 "3가지 차별화된 일정")
- 각 호출은 structured output(Claude는 tool use, GPT는 response_format)으로 아래 스키마 강제. provider별 SDK 호출부만 다르고 이후 파이프라인은 동일한 Pydantic 스키마로 통일:
```python
class CandidateDraft(BaseModel):
    title: str
    activities: list[ActivityDraft]  # 장소명, 카테고리, 시작~종료 시간, 예상 비용대
    rationale: str  # synthesize 단계에서 유사도 비교·검증 근거로 사용
```
- 장소는 이 단계에서 **실존 장소 DB/네이버 지역검색 API로 후보 좌표 riddle 없이** LLM이 알고 있는 이름만 던지지 않도록, 프롬프트에 사전 조회한 "지역 내 카테고리별 장소 후보 목록"(네이버 지역검색 결과)을 컨텍스트로 주입 — LLM은 이 목록 안에서만 선택하도록 지시 (환각 방지)
- `regions`가 여러 개면 각 지역마다 네이버 지역검색을 호출해서 병합한다
  (`app/services/naver_local_search.py`의 `search_places_for_regions()`, 이 함수를
  부를 POST /schedules 라우터는 아직 없음 — 함수 먼저, 라우터는 나중인 패턴) —
  지역별로 결과가 섞인 채로 `place_candidates`에 들어가므로 Step2 프롬프트는
  "이 지역들 전체에서" 고르라고 지시할 뿐, 지역별로 분리해서 활동을 배정하지 않는다.
- **`PreferenceTag.verifiable`에 따라 요구 강도를 다르게 지시(2026-08-07 결정)**:
  `verifiable=True`(해산물 등)는 `place_candidates`의 카테고리·이름으로 명확히
  판단되면 하드 제약(확실히 반영/배제). `verifiable=False`(사람 많은 곳, 조용한
  분위기 등)는 검증할 데이터가 없으므로 소프트 신호로만 — 장소 유형(관광명소 vs
  동네 가게)으로 미루어 최대한 반영하되 보장하지 않는다고 프롬프트에 명시. 활동
  설명(`rationale`)도 "사람이 없습니다"처럼 단정하지 말고 "비교적 한산한 편인
  곳으로 골랐어요"처럼 hedge된 표현을 쓰도록 지시 — 검증 못 한 걸 확신하는 것처럼
  말하면 실제와 다를 때 사용자 신뢰를 잃음

### Step 3. 검증·병합 (Aggregator) — `synthesize_and_validate()`
- **Step4(이동 동선 보강)보다 먼저 실행된다(2026-08-10 파이프라인 순서 재설계 —
  파일명도 `synthesize_step4.py` → `synthesize_step3.py`로 변경)** — 이 단계가
  보는 건 Step2의 장소·시간(좌표 기반 추정 버퍼 포함)뿐이고, 아직 실제
  이동경로는 없다. 경로 데이터 없이 검증 가능하도록 설계된 이유는 위 "1. 전체
  아키텍처" 참고
- MoA의 핵심 단계: Step 2에서 나온 3개 초안 + 예산 초과 여부를 **하나의 LLM 호출**에 모두 전달
- **왜 후보마다 따로(3번) 호출하지 않고 1번에 다 넣나**: 이 단계가 하는 일 중 하나가
  "후보끼리 서로 비교"인데, 후보 하나씩 따로 호출하면 그 호출은 다른 후보를
  볼 방법이 없음. 3개를 한 번에 넣어야 "A랑 C가 장소 2개 겹친다" 같은 비교
  판단이 가능함
- Step 2에서 장소·순서·시간은 이미 다 확정됨(이동경로는 아직 없음 — Step4는 사용자가
  후보를 고른 뒤에 실행) — Step 3는 그 구조를 재배치하지 않는다. 이 단계가 하는 일은
  구조가 아니라 **판단**:
  1. 예산/시간/조건 위반 여부 재검증 (규칙 기반 사전 필터링 + LLM 정성 판단 병행)
  2. **후보 간 유사도 검사**: LLM 호출 전에 규칙 기반(활동 이름 겹치는 비율 등)으로
     먼저 계산해서, 겹침이 심하면 그 정보를 프롬프트 컨텍스트로 얹어 "겹치는 후보는
     대체안으로 바꿔라"고 지시. 새 재시도 경로를 따로 만들지 않고 아래 3번 재시도
     메커니즘에 태움 (2026-08-07 결정 — 관점을 다르게 줘도 결과가 수렴할 수 있다는
     문제 제기에서 나옴)
  3. 위반이 심한 후보는 드롭하고, 필요시 해당 관점으로 재생성 1회 요청 (최대
     1회 재시도, 무한루프 방지). 위반 종류마다 강도가 다르다 — **활동 간 시간
     겹침은 항상 엄격**(구조적으로 불가능한 일정이라 예외 없이 드롭+재생성).
     **time_range 경계 초과와 예산 초과는 관대(soft)**: 둘 다 애초에 추정치
     기반이라(이동시간은 Step4의 실측 전엔 여유시간 추정일 뿐, 가격은
     `price_range_per_person`도 추정 범위) 근소한 초과(시간은 30분~1시간
     안팎, 예산은 1인 예산의 15~20% 안팎 — 정확한 값은 이 단계 구현 시 실측하며
     확정)는 드롭하지 않고 `feasibility_warning`에 경고만 채워서 살려두고
     (예: "예정보다 약 20분 더 걸리고, 예산도 약 3,000원 더 필요해요"), 관용
     범위를 크게 넘을 때만 하드 위반으로 드롭+재생성한다 (2026-08-09 결정 —
     상세 근거는 `docs/AI파이프라인_Step별_설계_2026-08-09.md` Step3 참고)
  4. 살아남은 후보 각각에 사용자에게 보여줄 한줄 요약(`why_recommended`) 생성 —
     **개수는 3개를 억지로 보장하지 않는다**: 재생성 1회까지 해도 일부 관점이
     실패하면 남은 개수(2개, 1개)를 그대로 보여준다 (2026-08-09 결정)
- **랭킹을 매기지 않는다**: 3개는 서로 다른 관점(가성비/동선최소화/취향반영)으로
  만들어진 것이라 "AI가 뽑은 1등"이 아니라 **동등한 선택지 3개**로 제시한다.
  `candidate_id`도 순위를 암시하는 숫자(1/2/3)가 아니라 `A`/`B`/`C` 문자를 쓰는
  이유가 이거다. `why_recommended`는 "왜 1등인지"가 아니라 "이 후보의 강점이
  뭔지"를 설명하는 문장 (2026-08-07 결정 — 순위 매길지 여부를 논의하고 확정)
- 출력: `ScheduleResponse`(단, 이 시점엔 `routes`가 빈 리스트 — 기능명세서의 "3가지
  후보, 각 후보에 시작·종료시간/활동/장소/1인당 비용/구간별 동선·교통비 포함"
  요구사항 중 구간별 동선·교통비는 Step4가 채운다)
- 유효한 후보가 **0개**일 때만 `InfeasibleResponse`로 사유 + 완화 가능한 조건 제안 반환 (기능명세서 §1, §6 요구사항). 프런트는 "생성 가능한 일정이 없어요 ㅠㅠ 조건을 다시 설정해주세요" 안내 + 조건 입력 화면으로 돌아가는 버튼을 보여준다 (2026-08-09 결정)

### Step 4. 이동 동선 보강 — `enrich_routes()` (LLM 안 씀, ODsay 대중교통 길찾기 API만, 구현 완료)
- Step 2에서 나온 각 후보의 장소 시퀀스는 이미 확정(순서·시간 포함) — 이 단계는 그
  구간 사이사이에 이동 정보만 채워 넣는다. 장소·순서를 재배치하지 않음
- **3개 후보 전부가 아니라 사용자가 선택한 1개에만 실행(2026-08-10, 파일명도
  `enrich_step3.py` → `enrich_step4.py`로 변경)**: Step3까지 끝나면 경로 없는 후보
  3개를 먼저 보여주고, 사용자가 하나를 고른 뒤에만 이 단계를 돌린다 — ODsay
  Basic(일 1,000건) 낭비 방지. 위 "1. 전체 아키텍처" 참고
- **프로바이더 — ODsay**(국내 대중교통 길찾기 전문 API, 무료 Basic 등급 일
  1,000건, 네이버 지도→카카오모빌리티를 거쳐 최종 결정, 2026-08-09). Step2가 쓰는
  네이버 지역검색과 프로바이더가 달라지지만, 길찾기는 좌표만 있으면 되는 문제라
  무관하게 동작함 — 네이버 지역검색의 mapx/mapy는 **이미 WGS84 경도/위도 ×
  10^7**이라 별도 좌표계 변환이 필요 없다(실측 확인, 2026-08-10). 대중교통 경로에
  도보 구간·요금·환승 횟수가 포함되고, 출발-도착이 700m 이내면 에러(`-98`)를
  반환해 이 경우 직선거리 기반 도보로 폴백한다. 영업시간은 두 API 모두 안 줘서
  (실측 확인) 자동 확인은 포기하고 `info_needs_check=True` + 네이버 지도 링크로
  사용자가 직접 확인하게 안내한다. 출발 시각 파라미터가 없어 막차/첫차 확인도
  같은 방식(포기 + 사용자 자기확인 안내)으로 처리한다
  (`docs/AI파이프라인_Step별_설계_2026-08-09.md` Step4 참고)
- **구간당 교통수단 옵션을 여러 개 반환**하고 자동으로 하나만 골라서 넣지 않는다
  (`RouteSegment.options: list[RouteOption]`, `recommended_mode`는 기본 선택값일
  뿐). 사용자가 원치 않는 교통편이 자동으로 확정되면 "AI가 대신 일정을 짜준다"는
  가치가 아니라 UX가 오히려 깨진다는 판단 (2026-08-07 결정). 차량(car) 옵션은
  프로바이더 미정으로 보류 — 스키마는 유지해 나중에 확장 가능
- Step2는 좌표 기반 직선거리로 활동 사이 시간을 미리 추정해둘 뿐이라, 이 단계가
  실제 이동시간을 알아내면 그 추정과 비교해 이후 활동들의 `start_time`/`end_time`을
  보정한다(초과분은 반드시 보정, 60분 넘는 여유만 당김 — 사용자가 다른 옵션을
  고르는 경우도 같은 로직 재사용)
- 실제 이동시간을 반영한 최종 일정이 `time_range`를 넘기면 `feasibility_warning`
  플래그로 알린다

### Step 5. 피드백 반영 루프 — `apply_feedback()`
사용자가 후보 하나를 고르고 피드백(텍스트 or 옵션)을 주면:
1. `parse_feedback()`: 자유 텍스트 피드백을 LLM 1회 호출로 "변경 대상 필드 + 방향"으로 구조화 (예: `{"field": "budget_per_person", "delta": +10000}` 또는 `{"field": "activity[1]", "action": "replace", "reason": "실내 아닌 곳으로"}`)
2. 구조화된 변경사항 + 기존 확정 일정을 컨텍스트로 Step 2~4를 **부분 재실행** (전체 재생성이 아니라 변경된 활동만 다시 채우는 프롬프트로 토큰/비용 절약)
3. 반영 불가 시 Step 3와 동일한 방식으로 사유 + 조정 가능 조건 안내

### 파이프라인 오류/타임아웃 처리
- 각 LLM 호출에 개별 timeout(예: 20초) + 실패 시 해당 관점만 스킵하고 나머지 후보로 진행 (완전 실패는 전체 관점이 다 실패했을 때만)
- 사용자에게는 "일정 생성 중" 로딩 상태를 SSE나 폴링으로 노출할지는 UX 결정 사항 — MVP는 단순 로딩 스피너 + 동기 응답으로 시작, 응답 시간이 체감상 길면 그때 스트리밍 도입

## 5. DB 스키마 전체 요약

```python
class User(SQLModel, table=True): ...          # 2.3
class LLMCredential(SQLModel, table=True): ...  # 3.3

class ScheduleSession(SQLModel, table=True):
    id: UUID = Field(primary_key=True, default_factory=uuid4)
    user_id: UUID = Field(foreign_key="user.id")  # 로그인 필수 가정이므로 non-null
    conditions: dict = Field(sa_column=Column(JSONB))       # NormalizedConditions
    candidates: dict = Field(sa_column=Column(JSONB))       # ScheduleResponse — Step3 직후엔
        # 경로 없는 3개, 사용자가 하나를 고르면 Step4(enrich_routes) 결과로 그 레코드를
        # 갱신(2026-08-10 파이프라인 순서 재설계, 1. 전체 아키텍처 참고). 정확한 갱신
        # 방식(전체 컬럼 재작성 vs 선택된 candidate_id만 patch)은 라우터 구현 시 확정.
    status: str = "draft"  # draft | confirmed
    created_at: datetime = Field(default_factory=datetime.utcnow)

class FeedbackMessage(SQLModel, table=True):
    id: UUID = Field(primary_key=True, default_factory=uuid4)
    session_id: UUID = Field(foreign_key="scheduleseession.id")
    role: str  # user | system
    content: str
    created_at: datetime = Field(default_factory=datetime.utcnow)

class ShareLink(SQLModel, table=True):
    id: UUID = Field(primary_key=True, default_factory=uuid4)
    session_id: UUID = Field(foreign_key="scheduleseession.id")
    slug: str = Field(unique=True, index=True)  # 짧은 랜덤 문자열, URL에 사용
    created_at: datetime = Field(default_factory=datetime.utcnow)
```

- `candidates`/`conditions`를 JSONB로 저장하는 이유: 파이프라인 스키마(Pydantic 모델)가 초기에 자주 바뀔 시기이므로, 매번 마이그레이션하지 않고 유연하게 대응 (스키마가 안정화되면 정규화 테이블로 리팩터링 검토)
- `ShareLink` 조회 API는 인증 없이 `GET /share/{slug}` 공개 — 기능명세서 §5 요구사항 그대로

## 6. API 엔드포인트 개요

```
POST   /auth/google                 Google id_token 검증 → 세션 JWT 발급
GET    /me                          현재 로그인 사용자 정보
POST   /me/llm-credential           API 키 등록 (검증 후 저장)
```
