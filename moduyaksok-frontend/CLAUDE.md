# 모두약속 — 프런트엔드 개발 방법론

실행/디자인 시스템/컴포넌트 목록·화면 매핑은 `README.md` 참고. 여기는 "왜 이렇게
개발하기로 했는지"만 남긴다 — 새 기능을 이 프로젝트 방식대로 만들 때 참고할 것.

## 상태 영속화는 항상 localStorage, 로그아웃 시 전부 정리
- 새로고침해도 유지돼야 하는 상태(로그인 토큰, API 키 등록 상태·마스킹된 값 등)는
  `localStorage`에 저장하는 패턴으로 통일한다 — 매번 서버에 물어보지 않고 로컬에서
  바로 복원.
- `logout()` 액션은 로그인 토큰뿐 아니라 **이 패턴으로 저장한 모든 키**를 같이
  지울 것. 하나라도 빠뜨리면 같은 브라우저에서 다른 계정으로 로그인했을 때 이전
  사용자의 상태(API 키 등록 여부 등)가 새 사용자에게 그대로 새어나간다.

## 네이티브 `<select>`의 한계 — 옵션 패널까지 스타일 입혀야 하면 커스텀 컴포넌트
- 네이티브 `<select>`는 닫힌 상태 박스만 CSS로 스타일 가능하고, 펼쳐지는 옵션
  목록은 브라우저/OS가 그려서 손그림 디자인 시스템을 못 입힌다.
- 시각적 일관성이 중요한 경우 `DoodleSelect`처럼 버튼 + 직접 그린 리스트로 구현할
  것(키보드 네비게이션·바깥 클릭 시 닫기 포함). 목록이 짧고 스타일이 안 중요하면
  네이티브 select도 무방 — 매번 커스텀할 필요는 없다.

## 자유 텍스트 vs 고정 선택지 — 도메인이 열려있으면 자유 텍스트 + 백엔드 정규화
- "선호/비선호"처럼 사용자가 뭘 말할지 미리 다 정의할 수 없는 입력은, 프런트에서
  태그 칩으로 제한하지 말고 자유 텍스트로 받고 백엔드(AI 파이프라인 Step1)가
  구조화하게 설계한다. 프런트가 유한한 옵션 목록을 강제하면 표현의 다양성을 잃음.
- 자유 텍스트를 받을 땐 글자수 제한을 꼭 걸 것(`DoodleTextarea`의 `maxlength` prop)
  — 그대로 LLM 프롬프트에 들어가는 값이라 무제한으로 두면 안 된다.

## 디자인 시스템 제약은 타협하지 않기
- 색은 `ink`/`red`/`paper` 3개뿐 — 새 강조색 추가 금지. 상태 표현은 색 대신
  아이콘/굵기로.
- 라이트 테마 고정(다크모드 없음) — 노트 종이 메타포는 색을 반전하면 깨진다.
- 새 폼 컨트롤을 추가할 땐 원시 HTML 태그를 뷰에 바로 쓰지 말고 `Doodle*` 래퍼
  컴포넌트를 만들 것 — 기존 컴포넌트들과 스타일 일관성 유지.

## UI 변경 검증
- 브라우저로 직접 인터랙션 테스트를 못 하는 상황이면 최소한 `npm run build`
  (타입체크 + 프로덕션 빌드)까지는 돌려서 확인하고, 실제 브라우저 확인은 안
  했다고 명시적으로 말할 것 — 확인 안 한 걸 확인한 것처럼 보고하지 않는다.
